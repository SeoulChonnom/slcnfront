# 백엔드 에이전트 요청 프롬프트 — 홈 `Memory Chronicle` API 개발 검토

> 작성일: 2026-08-28
> 사용법: 아래 `---` 사이 본문을 그대로 백엔드 개발 에이전트에게 전달한다. 프롬프트는 자체 완결형이며, 외부 문서 참조 없이 그대로 실행 가능하다.

---

너는 SLCN(Seoul Chonnom) 백엔드(Spring Boot, base path `/api`) 를 담당하는 시니어 백엔드 엔지니어다.

프론트엔드 팀이 홈 화면(`Memory Chronicle`) 재설계를 마쳤고, 그 과정에서 향후 필요해질 수 있는 백엔드 변경 후보를 정리했다. 이 요청의 목적은 **그 후보들에 대한 개발 검토(feasibility review)를 수행하는 것**이다.

## 0. 이 작업의 성격 — 구현이 아니라 검토다

**이번 작업에서 프로덕션 코드를 변경하지 마라.** 새 endpoint를 만들거나, 스키마를 바꾸거나, 마이그레이션을 추가하지 마라.

너의 산출물은 **검토 보고서 한 건**이다. 각 변경 후보에 대해 다음을 판단해서 답하는 것이 목표다.

- 지금 필요한가? (현재 데이터 규모·성능 실측 기준)
- 구현 가능한가? 어떤 방식으로 구현하는 것이 이 코드베이스에 맞는가?
- 비용은 얼마나 드는가? (변경 범위, 인덱스/스키마 영향, 리스크)
- 착수 / 보류 / 불필요 중 무엇을 권고하는가?

읽기 전용 조사(코드 탐색, SELECT 쿼리, 로컬 API 호출, 응답 헤더 확인)는 필요한 만큼 자유롭게 수행해도 된다. 쓰기 변경만 하지 마라.

## 1. 배경 — 프론트엔드의 현재 동작

프론트엔드는 이미 백엔드 변경 없이 홈 화면을 동작시키고 있다. 현재 방식은 다음과 같다.

- `GET /travels` 로 여행 목록 **전체**를 받아 브라우저 메모리에서 최신순 정렬, 연도 필터, 텍스트 검색을 수행한다. 검색 대상 필드는 `title`, `region`, `oneLineReview` 세 개뿐이다.
- 연도 rail(연도 이동 UI)의 연도 목록도 로드된 전체 여행에서 파생한다.
- 표지 이미지는 `GET /assets/files/{fileId}` 를 Blob으로 요청한다. 최신 여행 표지 1개 + 현재 필터 결과 앞쪽 최대 12개, 즉 **1회 진입당 최대 13건**이다. 최신 표지는 `fetchPriority="high"`, 나머지는 `loading="lazy"` 로 처리한다.
- 여행 / 일정 / 나들이를 **각각 독립된 요청**으로 읽고 소스별 loading·error·retry 상태를 따로 관리한다. 하나가 실패해도 나머지는 계속 표시되며, 세 요청이 모두 실패할 때만 전체 오류가 된다.
- 일정은 `GET /schedule/now` 응답에서 현재 시각 이후 가장 가까운 최대 3개를 클라이언트가 골라 표시한다.
- 표지 다운로드 실패나 표지 없음은 텍스트 fallback으로 처리하며, 여행 기록 자체를 실패시키지 않는다.

**즉, 지금 프론트가 막혀 있는 기능은 없다.** 아래 후보들은 "규모가 커지거나 새 제품 요구가 생겼을 때"를 대비한 것이며, 검토의 첫 번째 임무는 그 시점이 이미 도래했는지 실측으로 확인하는 것이다.

참고로 이 서비스의 주 사용자는 두 명이다. 대규모 트래픽을 전제로 과설계하지 마라.

## 2. 프론트가 현재 의존하는 계약

아래는 프론트엔드가 실제로 파싱하고 있는 응답 형태다. **백엔드 저장소의 실제 구현과 대조해 차이가 있으면 그 사실 자체를 보고하라.**

| Endpoint | 프론트가 기대하는 응답 |
| --- | --- |
| `GET /travels` | `TravelRdo[]` |
| `GET /travels/{travelId}` | 여행 상세 |
| `GET /trips` | `TripListRdo[]` |
| `GET /schedule/now` | `ScheduleRdo[]` (이번 달 일정) |
| `GET /assets/files/{fileId}` | 이미지 바이트 |

주요 필드:

- `TravelRdo`: `id`, `travelId`, `title`, `region`, `startDate`, `endDate`, `cover`(`FileBoxItemRdo`), `oneLineReview`, `nights`, `days`, `tags`
- `FileBoxItemRdo`: `id`, `fileAssetId`, `targetType`, `targetId`, `role`(`COVER` 등), `caption`, `sortOrder`, `file`
- `TripListRdo`: `id`, `date`, `type`, `name`, `logo`
- `ScheduleRdo`: `id`, `calendarId`, `title`, `body`, `start`, `end`, `allDay`, `location`

표지 식별자는 `TravelRdo.cover.fileAssetId` 이며, 프론트는 이 ID로 `GET /assets/files/{fileId}` 를 호출한다.

인증은 `X-AUTH-TOKEN: <access-token>` 헤더 기반이고, 응답은 토큰이 허용하는 로그인 사용자/커플 스코프로 제한된다.

## 3. 검토 항목 A (최우선) — 현황 실측

후보 기능의 필요 여부를 판단할 근거가 현재 전혀 없다. 다음을 **실제로 측정**해서 보고하라. 추정치는 받지 않는다.

1. 여행 레코드 전체 수
2. 인증된 사용자 기준 `GET /travels` 응답 본문 크기 (bytes, gzip 전/후)
3. `GET /travels` 응답 시간 p50 / p95. 트래픽이 없어 p95 산출이 불가능하면 그 사실과 대체 측정 방법(예: N회 반복 호출)을 명시하라
4. 표지 이미지 1건의 평균/최대 바이트, 그리고 홈 1회 진입 시 발생하는 이미지 다운로드 총 바이트 (최대 13건 기준)
5. `GET /assets/files/{fileId}` 의 현재 응답 헤더 실측값 — `Content-Type`, `Content-Length`, `ETag`, `Cache-Control` 유무
6. `travels` 관련 테이블의 현재 인덱스 구성 (특히 `startDate`, 소유자/커플 스코프 컬럼)

측정에 사용한 쿼리·명령·로그 위치를 함께 남겨 재현 가능하게 하라.

그리고 측정값을 아래 임계치와 대조해 **항목별로 충족/미충족을 명시**하라.

- 여행 기록 200개 초과
- `GET /travels` 응답 본문 1 MiB 초과
- 홈 진입 시 `GET /travels` p95 500 ms 초과

이 임계치들은 관측 후 조정 가능한 가드레일이다. 실측 결과 임계치가 비현실적이라고 판단되면 **근거와 함께 다른 임계치를 역제안하라.**

## 4. 검토 항목 B — 변경 후보별 개발 검토

아래 각 후보에 대해 **구현하지 말고**, 3장 실측 결과에 비추어 검토 의견을 작성하라. 후보 설명에 적힌 스펙 초안은 프론트 측 제안이며 확정안이 아니다. **더 나은 설계가 있으면 역제안하라.**

### 후보 1. 여행 목록의 커서 페이지네이션 + 서버 검색

문제 상황: `GET /travels` 는 전체 배열을 반환하고 페이지 경계가 없다. 기록이 늘면 첫 진입 전송량·파싱 시간·DOM 수가 증가하고, 연도 rail에 표시할 전체 연도를 알 수 없으며, 검색 결과가 로드된 범위에만 한정된다.

프론트 제안 초안:

```http
GET /travels/search?q={urlencoded-text}&year=YYYY&limit=50&cursor={opaque}
```

- `q` 생략 가능. 공백 trim 후 대소문자 비구분 부분 문자열로 `title`, `region`, `oneLineReview` 세 필드에만 적용
- `year` 는 `startDate` 의 네 자리 연도
- `limit` 기본 50 / 최대 100, `cursor` 는 첫 페이지에서 생략하는 불투명 커서
- 정렬은 `startDate DESC, id ASC` 고정 (출하된 클라이언트 정렬과 일치시켜 커서 페이지 간 중복·누락 방지)
- 응답은 `{ items: TravelRdo[], meta: { limit, nextCursor, hasNext, total, availableYears } }` 형태. `nextCursor` 는 마지막 페이지에서 `null`, `availableYears` 는 현재 페이지가 아니라 **스코프 전체**의 연도 목록. `total` 계산이 비싸면 생략 가능하나 `hasNext`·`nextCursor`·`availableYears` 는 필수
- 기존 `GET /travels` 배열 응답은 유지하고 **새 endpoint를 additive로 추가**하는 전제

검토해서 답할 것:

- 실측 기준으로 지금 필요한가?
- 커서 인코딩을 어떻게 할 것인가? (`startDate` + `id` 복합 키 기반 keyset 방식이 이 스키마에서 가능한가)
- `q` 부분 문자열 검색을 현재 DB에서 어떻게 처리할 것인가? 인덱스로 커버 가능한가, full scan이 되는가, 별도 검색 인프라가 필요한가?
- `availableYears` 와 `total` 을 매 요청 계산할 때의 비용은?
- 필요한 인덱스 추가와 그 영향
- 예상 작업량과 리스크

### 후보 2. 표지 이미지 변형 + HTTP 캐시

문제 상황: 홈은 표지 파일 ID마다 원본 바이트를 요청한다. 요청 크기 변형, 썸네일 URL, `ETag`/캐시 정책, 이미지 차원 메타데이터가 계약에 정의되어 있지 않다. 저대역폭 환경에서 큰 원본을 작은 행 썸네일에 내려받는 비용이 커질 수 있다.

프론트 제안 초안:

```http
GET /assets/files/{fileId}?variant=home-feature&width=960&format=webp
GET /assets/files/{fileId}?variant=home-thumb&width=320&format=webp
```

- 응답 본문은 JSON envelope가 아니라 이미지 바이트 유지
- 실제 형식에 맞는 `Content-Type`, `Content-Length`, 재검증 가능한 `ETag`, `Cache-Control: private, max-age=86400`
- `immutable` 은 파일 ID 불변이 운영상 보장되는 경우에만
- query 없는 기존 요청은 기존 이미지 바이트를 그대로 반환 (하위 호환)

검토해서 답할 것:

- 실측한 이미지 바이트 기준으로 지금 병목인가?
- 리사이즈를 어디서 수행할 것인가? (요청 시 온디맨드 변환 vs 업로드 시 사전 생성) 각 방식의 저장 비용·CPU 비용·캐시 전략 비교
- 현재 파일 저장소 구조에서 변형본을 어디에 둘 것인가?
- `ETag` 를 무엇으로 생성할 것인가? 파일 ID가 실제로 불변인가?
- `Cache-Control: private` 가 현재 인증 구조에서 안전한가?
- 변형 파라미터를 지원하지 않을 때 400/404 중 무엇을 반환할지 (프론트는 실패 시 원본 endpoint로 재시도한다)

### 후보 3. 월 경계를 넘는 다음 일정 endpoint

문제 상황: `GET /schedule/now` 는 이번 달 일정만 정의되어 있어, 월말에 다음 달 일정만 남은 경우 홈의 일정 영역이 비어 보일 수 있다. 다만 실제 누락 사례는 아직 확인되지 않았다.

프론트 제안 초안:

```http
GET /schedule/next?from={urlencoded-ISO-8601}&limit=3
```

- 응답은 기존 `ScheduleRdo[]` 유지. `from` 이후 일정만 `start` 오름차순으로 최대 `limit` 개
- 기존 `GET /schedule/now` 는 그대로 두고 additive 추가

검토해서 답할 것:

- 현재 `GET /schedule/now` 구현이 실제로 이번 달 경계에서 잘리는가? **코드로 확인하라.** 이미 월 경계를 넘겨 반환한다면 이 후보는 불필요하다
- 필요하다면 신규 endpoint가 맞는가, 기존 endpoint에 파라미터를 추가하는 편이 나은가?
- 반복 일정(recurring)이 있다면 `from` 이후 조회에 어떤 영향이 있는가?
- 이는 제품 결정이 선행되어야 하는 항목이다. 백엔드 관점의 판단 근거만 제시하고 임의로 결정하지 마라

### 후보 4. 공통 오류 응답 형식

문제 상황: 위 endpoint들의 4xx/5xx 공통 오류 body가 정의되어 있지 않다. 프론트는 JSON에 `message` 가 있으면 읽고, 없으면 HTTP 상태/본문으로 오류 메시지를 만든다.

프론트 제안 초안:

```json
{ "code": "SCHEDULE_UNAVAILABLE", "message": "...", "retryable": true, "requestId": "req_..." }
```

- HTTP status는 의미에 맞게 유지하고, 기존 client가 읽는 `message` 키는 **반드시 보존**
- body 없는 기존 오류 응답도 계속 유효해야 함

검토해서 답할 것:

- 현재 예외 처리 구조에서 전역 핸들러로 표준화 가능한가? 이미 유사한 구조가 있는가?
- `requestId` 를 발급/로그 상관관계에 쓸 수 있는 기반(MDC, trace ID)이 있는가?
- 우선순위가 낮은 항목이다. 도입 비용이 크면 "보류" 권고로 충분하다

## 5. 검토 시 지켜야 할 제약

1. **하위 호환:** 기존 `GET /travels`, `GET /trips`, `GET /schedule/now`, `GET /assets/files/{fileId}` 의 경로와 성공 응답 형태를 바꾸는 안은 제안하지 마라. 특히 `GET /travels` 를 `{ items, meta }` envelope로 감싸는 변경은 현재 프론트 파서를 깨뜨린다. 모든 변경은 additive여야 한다.
2. **인증/스코프:** 신규 endpoint와 변형 이미지 요청도 기존과 동일하게 `X-AUTH-TOKEN` 을 요구하고, 토큰이 허용하는 로그인 사용자/커플 스코프의 데이터만 반환하는 것을 전제로 검토하라.
3. **공개 접근 경로 금지:** public endpoint, 새 public key, 서명 없는 공개 이미지 URL, 외부 공유용 URL은 검토 범위가 아니다.
4. **비범위:** 여행·나들이 통합 endpoint, 파일 경로를 공개 URL로 전환, 외부 공유/내보내기, 상세 페이지 계약 변경. 제안하지 마라.
5. **과설계 금지:** 사용자 2명 규모다. 실측 근거 없이 캐시 계층, 검색 엔진, 이벤트 파이프라인 같은 인프라 추가를 제안하지 마라.

## 6. 산출물 형식

다음 구조의 Markdown 보고서 한 건으로 답하라.

1. **요약** — 4개 후보 각각에 대한 권고를 한 줄씩 (착수 / 보류 / 불필요)
2. **현황 실측** — 3장의 6개 항목을 표로. 각 값에 측정 방법(명령/쿼리) 병기
3. **임계치 판정** — 항목별 충족/미충족 + 근거. 임계치 자체에 대한 역제안이 있으면 함께
4. **후보별 검토** — 후보 1~4 각각에 대해: 필요성 판단 / 권장 구현 방식 / 스키마·인덱스 영향 / 예상 작업량 / 리스크 / 대안이나 역제안
5. **기존 계약과의 차이** — 프론트가 기대하는 계약(2장)과 백엔드 실제 구현이 다른 지점이 있으면 여기에
6. **프론트에 확인이 필요한 사항** — 검토 과정에서 생긴 질문
7. **제품 결정이 필요한 사항** — 백엔드가 판단할 수 없는 항목 (예: 후보 3의 제품 요구 확정 여부)

## 7. 완료 기준

- 추측으로 답하지 마라. 실측값은 **실제 실행 출력**이어야 한다.
- 조사하지 **못한** 항목은 무엇을 왜 확인하지 못했는지 명시하라.
- 프로덕션 코드를 변경하지 않은 상태로 보고서만 제출하는 것이 이 작업의 정상적인 완료 상태다.
- "실측 결과 4개 후보 모두 현재는 불필요"라는 결론도 유효한 결과다. 억지로 착수 권고를 만들지 마라.
