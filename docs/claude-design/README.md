# Claude Design 리디자인 자료와 진행 가이드

서비스의 브랜드, 레이아웃, 화면을 모두 새로 만드는 리디자인 자료를 모은 폴더다. 이 문서(README)는 **사람이 읽는 안내서**다. Claude Design에는 넘기지 않는다.

- **디자인을 진행하는 분**: [1. 시작하기 전에](#1-시작하기-전에)부터 [6. 개발 담당에게 넘기기](#6-개발-담당에게-넘기기)까지 순서대로 읽으면 된다. 디자인이나 개발 지식이 없어도 따라 할 수 있게 썼다.
- **개발 담당**: [7. 자료 상세](#7-자료-상세)에 문서 구성과 작성 원칙을 정리했다.

---

## 1. 시작하기 전에

### 이번 작업이 하는 일

지금 쓰고 있는 서비스의 **겉모습을 전부 새로 만든다.** 이름, 로고, 색, 글꼴, 화면 배치까지 모두 바뀐다. 다만 **기능은 그대로**다. 지금 할 수 있는 일은 새 디자인에서도 전부 할 수 있어야 한다.

### 역할 분담

| 누가 | 하는 일 |
|---|---|
| **디자인 진행자** (이 안내서를 읽는 분) | 브랜드를 정하고, Claude Design과 대화하며 시안을 만들고, 마음에 드는 방향으로 다듬는다 |
| **Claude Design** | 요청에 따라 로고, 색, 화면 시안을 실제로 그려 준다 |
| **개발 담당** | 완성된 시안을 받아 실제 서비스 코드로 옮긴다. 기능 관련 질문에 답한다 |

디자인 진행자는 **"무엇이 마음에 드는지"를 결정하는 사람**이다. 그리는 일은 Claude Design이 하고, 기능이 빠졌는지는 함께 받은 문서가 지켜 준다. 전문 용어를 몰라도 괜찮다. 좋고 싫음을 말로 설명할 수 있으면 충분하다.

### 꼭 기억할 세 가지

1. **기능은 바꾸지 않는다.** 새 기능을 넣거나 있는 기능을 빼고 싶다면 Claude Design에 바로 요청하지 말고 개발 담당과 먼저 상의한다.
2. **옛 디자인은 보여 주지 않는다.** 지금 서비스의 캡처, 옛 로고, 옛 디자인 문서를 Claude Design에 올리면 새 디자인이 옛 모습을 닮아 버린다.
3. **한 번에 다 만들지 않는다.** 브랜드 → 기본 규칙 → 대표 화면 → 전체 화면 순서로, 단계마다 확정하고 넘어간다.

### Claude Design에 올릴 파일

| 올릴 것 | 올리지 말 것 |
|---|---|
| 이 폴더에서 **`README.md`를 뺀 모든 파일** (`00-brief.md`부터 `08-content-samples.md`까지) | 이 `README.md` |
| 직접 만든 취향 자료 (아래 0단계) | 지금 서비스의 화면 캡처 |
| 확정한 브랜드 정리 (1단계 결과) | 옛 로고, 기존 `DESIGN.md`, 기존 프로토타입 HTML |

- `00-brief.md`는 Claude Design에게 "무엇을, 어떤 조건으로 만들어야 하는지"를 알려 주는 의뢰서다. 디자인 진행자도 한 번 읽어 두면 좋다.
- 나머지 파일은 기능 명세라서 길다. 디자인 진행자가 다 읽을 필요는 없다.
- Claude Design 화면의 버튼이나 메뉴 이름은 업데이트로 바뀔 수 있다. 이 안내서의 표현과 다르면 비슷한 기능을 찾아 쓰면 된다.

## 2. 진행 순서 한눈에 보기

| 단계 | 하는 일 | 결과물 | 예상 대화 횟수 |
|---|---|---|---|
| 0. 취향 모으기 | 좋아하는 앱·사이트를 모으고 이유를 적는다 | 취향 메모 1장 | Claude Design 없이 진행 |
| 1. 브랜드 | 이름, 로고, 대표 색, 분위기를 정한다 | 브랜드 정리 1장 | 10~30회 |
| 2. 기본 규칙 | 색, 글꼴, 버튼 같은 공통 규칙을 정한다 | 디자인 시스템 | 10~30회 |
| 3. 대표 화면 | 중요한 화면 5개로 방향을 검증한다 | 대표 화면 시안 + 매핑표 | 20~50회 |
| 4. 전체 화면 | 나머지 화면과 모든 상태를 만든다 | 전체 시안 + 매핑표 | 영역별로 나눠 진행 |
| 5. 최종 점검 | 체크리스트로 빠진 것을 확인한다 | 점검 완료 | 5~10회 |
| 6. 넘기기 | 개발 담당에게 결과물을 전달한다 | HTML 프로토타입 + 디자인 문서 | – |

대화 횟수는 대략적인 감이다. 더 걸려도 괜찮다. 다만 같은 부분을 10번 넘게 고치고 있다면 [막혔을 때](#막혔을-때)를 본다.

**결정 메모를 꼭 남긴다.** 단계가 끝날 때마다 확정한 내용을 메모장이나 노션에 짧게 적어 둔다(예: "대표 색: 짙은 초록 #1F4D3A 확정, 글꼴: 둥근 고딕 계열"). 대화가 길어지면 Claude Design도 앞에서 정한 것을 잊을 수 있다. 그때 이 메모를 다시 붙여 넣으면 된다.

## 3. 단계별 진행 방법

### 0단계: 취향 모으기 (Claude Design 없이)

디자인을 모르는 사람이 가장 쉽게 원하는 것을 전달하는 방법은 **"이런 느낌"의 예시를 보여 주는 것**이다.

1. 평소 쓰면서 "보기 좋다"고 느낀 앱이나 웹사이트를 **3~5개** 고른다. 분야는 상관없다(가계부 앱, 쇼핑몰, 잡지 사이트 등).
2. 각각 화면을 캡처하고, **무엇이 좋은지 한 줄**을 적는다.
   - 예: "여백이 넉넉해서 답답하지 않다", "사진이 크게 나와서 시원하다", "색이 두 가지뿐이라 깔끔하다"
3. **싫은 예시도 1~2개** 모은다. "이런 건 아니다"도 큰 도움이 된다.
   - 예: "알록달록해서 정신없다", "글씨가 너무 작다"
4. 서비스를 **형용사 3개**로 표현해 본다.
   - 예: "차분한, 따뜻한, 기록장 같은" / "경쾌한, 밝은, 여행 같은"

다른 서비스의 캡처는 "느낌의 참고"로만 쓴다. 특정 서비스를 그대로 베껴 달라고 하지 않는다.

### 1단계: 브랜드

**목표**: 서비스 이름, 로고, 대표 색, 전체 분위기를 확정한다.

이름은 Claude Design에 들어가기 **전에** 정해 두는 것이 좋다. 이름이 정해져야 로고와 분위기가 따라 정해진다. 이름 후보를 함께 고민해 달라고 해도 되지만, 최종 결정은 사람이 한다.

**첫 프롬프트 예시** (파일을 모두 올린 뒤 그대로 붙여 넣고, `[ ]` 부분만 바꾼다)

```
첨부한 00-brief.md를 먼저 읽어 주세요. 개인 기록 웹 서비스의 디자인을 새로 만들려고 합니다.
이번 대화에서는 1단계 "브랜드"만 진행합니다. 화면 디자인은 아직 만들지 마세요.

- 서비스 이름: [새 이름]
- 이름에 담은 뜻: [예: 걸으며 모은 하루라는 뜻]
- 원하는 분위기 형용사: [차분한, 따뜻한, 기록장 같은]
- 좋아하는 예시와 이유: [첨부한 캡처 1~3, 각각 이유 한 줄]
- 피하고 싶은 느낌: [알록달록함, 너무 귀여운 캐릭터]

서로 다른 방향의 브랜드 시안 3개를 보여 주세요.
각 시안에는 로고(아이콘만 있는 버전, 이름까지 있는 버전), 대표 색 2~3개, 분위기 설명 한 줄을 넣어 주세요.
```

**다듬기 프롬프트 예시**

```
2번 시안의 색이 마음에 듭니다. 로고는 1번처럼 단순한 모양이면 좋겠어요.
2번 색 + 1번 로고 스타일로 다시 3가지 변형을 보여 주세요.
```

```
로고를 아주 작게(브라우저 탭 아이콘 크기, 16px) 줄였을 때와 어두운 배경 위에 놓았을 때도 보여 주세요.
```

**확정 프롬프트 예시**

```
브랜드를 확정합니다. 확정한 내용을 "브랜드 정리" 한 장으로 요약해 주세요.
이름, 로고 버전별 쓰임, 대표 색(색상 코드 포함), 분위기 설명이 들어가야 합니다.
앞으로 이 내용은 바꾸지 말아 주세요.
```

**넘어가기 전 확인**

- [ ] 로고가 작게 줄여도 알아볼 수 있다
- [ ] 로고가 밝은 배경과 어두운 배경에서 모두 잘 보인다
- [ ] 대표 색이 정해졌고 색상 코드가 결정 메모에 적혀 있다
- [ ] "브랜드 정리"를 파일로 저장했다

### 2단계: 기본 규칙 (디자인 시스템)

**목표**: 모든 화면에 공통으로 쓰일 규칙을 정한다. 색 조합, 글꼴과 글자 크기, 여백, 모서리 둥글기, 버튼과 입력칸 모양 등이다. 이 규칙이 정해지면 이후 화면이 일관되게 나온다.

**프롬프트 예시**

```
확정한 브랜드 정리를 바탕으로 2단계 "디자인 시스템"을 만들어 주세요. 00-brief.md의 5번 진행 단계 표를 따릅니다.

포함할 것:
- 밝은 화면용, 어두운 화면용 색 규칙
- 글꼴과 글자 크기 단계 (한글 본문이 편하게 읽혀야 합니다)
- 버튼, 입력칸, 선택 상자, 탭, 확인 창, 알림 같은 공통 부품
- 부품마다 평소, 마우스를 올렸을 때, 선택됐을 때, 누를 수 없을 때, 오류일 때 모습

부품들을 한 페이지에 모아서 보여 주세요.
```

**다듬기 프롬프트 예시**

```
본문 글씨가 조금 작게 느껴집니다. 한 단계 키워 주세요. 나머지 크기도 비율에 맞춰 같이 조정해 주세요.
```

```
어두운 화면에서 회색 글씨가 잘 안 보입니다. 00-brief.md의 접근성 기준(대비 4.5:1)을 만족하는지 확인하고 고쳐 주세요.
```

**넘어가기 전 확인**

- [ ] 밝은 화면과 어두운 화면을 둘 다 봤다
- [ ] 휴대폰 크기에서도 글씨가 편하게 읽힌다
- [ ] 버튼의 "누를 수 없음", 입력칸의 "오류" 모습이 있다
- [ ] 결정 메모에 "디자인 시스템 확정"과 주요 결정을 적었다

### 3단계: 대표 화면 5개

**목표**: 중요하고 복잡한 화면 5개를 먼저 만들어, 정한 규칙이 실제 화면에서도 괜찮은지 확인한다. 여기서 방향이 틀어지면 2단계로 돌아가 규칙을 고친다.

대표 화면은 `00-brief.md`에 정해져 있다: 홈, 여행 상세, 임장 지역 상세(지도 포함), 임장 계획 등록, 달력 월 보기.

**프롬프트 예시** (한 번에 한 화면씩 요청하는 것이 좋다)

```
3단계 대표 화면을 시작합니다. 먼저 "홈" 화면을 만들어 주세요.
- 01-home.md의 모든 기능 ID가 화면에 들어가야 합니다.
- 데이터는 08-content-samples.md의 "보통" 샘플을 써 주세요.
- 데스크톱(1440px)과 휴대폰(390px)을 둘 다 만들어 주세요.
- 다 만든 뒤 00-brief.md 형식의 기능 매핑표를 함께 주세요.
```

**극단 상황 확인 프롬프트 예시**

```
같은 화면에 08-content-samples.md의 "꽉 찬 경우" 데이터를 넣어 보여 주세요. 긴 제목이 넘치지 않는지 보고 싶어요.
```

```
이 화면의 불러오는 중, 데이터가 하나도 없을 때, 오류가 났을 때 모습도 보여 주세요.
```

**넘어가기 전 확인**

- [ ] 5개 화면 모두 데스크톱과 휴대폰 버전이 있다
- [ ] 각 화면의 기능 매핑표에 해당 문서의 기능 ID가 모두 들어 있다
- [ ] 꽉 찬 데이터와 빈 데이터에서도 화면이 깨지지 않는다
- [ ] 어두운 화면으로도 한 번씩 봤다

### 4단계: 전체 화면

**목표**: 나머지 모든 화면과 상태를 만든다. 양이 많으므로 **영역 하나씩** 진행한다. 권장 순서: 공통(로그인, 메뉴, 404) → 여행 → 나들이 → 임장 → 달력 → 신발 → 프로필.

**프롬프트 예시**

```
4단계를 진행합니다. 이번에는 "여행" 영역 전체입니다.
02-travel.md의 모든 화면과 상태를 확정한 디자인 시스템으로 만들어 주세요.
3단계에서 만든 여행 상세 화면과 같은 느낌을 유지해 주세요.
끝나면 02-travel.md의 모든 기능 ID에 대한 매핑표를 주세요. 빠진 ID가 있으면 따로 알려 주세요.
```

**관리자 화면 확인 프롬프트 예시**

```
이 영역에서 관리자만 쓰는 기능이 일반 사용자에게는 어떻게 보이는지(또는 안 보이는지) 두 경우를 나란히 보여 주세요.
```

**넘어가기 전 확인 (영역마다)**

- [ ] 해당 영역 문서의 모든 기능 ID가 매핑표에 있다
- [ ] 문서의 "상태"에 적힌 경우(불러오는 중, 빈 상태, 오류, 처리 중)가 모두 디자인돼 있다
- [ ] 문서에 "현재 문구"로 적힌 안내 문구의 뜻이 새 화면에도 살아 있다
- [ ] 앞 영역과 버튼, 색, 간격 느낌이 같다

### 5단계: 최종 점검

```
지금까지 만든 전체 시안을 점검해 주세요.
1. 00-common.md부터 07-profile.md까지의 모든 기능 ID가 매핑표에 있는지, 빠진 ID 목록
2. 데스크톱과 휴대폰 중 한쪽에만 있는 기능 목록과 그 이유
3. 디자인 시스템과 다르게 그려진 곳 목록
4. 어두운 화면에서 글씨가 잘 안 보이는 곳 목록
```

빠진 것이 나오면 해당 영역으로 돌아가 채운다. **빠진 기능 ID가 0개가 될 때까지** 6단계로 넘어가지 않는다.

## 4. 프롬프트 잘 쓰는 법

### 기본 원칙

| 원칙 | 이렇게 하지 말고 | 이렇게 |
|---|---|---|
| 느낌은 이유와 함께 | "더 예쁘게 해 주세요" | "사진이 더 크게 보였으면 해요. 지금은 글씨가 화면을 차지하는 느낌이에요" |
| 한 번에 한두 가지만 | 색, 글씨, 배치, 버튼을 한꺼번에 고쳐 달라고 하기 | "이번에는 색만 바꿔 주세요. 배치는 그대로 두세요" |
| 고를 수 있게 요청 | "좋은 걸로 하나 만들어 주세요" | "서로 다른 방향으로 3가지 보여 주세요" |
| 마음에 드는 것은 잠그기 | 말없이 다음 요청으로 넘어가기 | "이 색은 확정입니다. 앞으로 바꾸지 마세요" |
| 위치를 정확히 | "그거 좀 바꿔 주세요" | "휴대폰 화면 맨 아래 메뉴의 세 번째 아이콘" |
| 예시를 보여 주기 | 말로만 길게 설명하기 | 비슷한 느낌의 캡처를 첨부하고 "이 부분의 여백 느낌" |
| 근거 문서를 가리키기 | "기능 다 넣어 주세요" | "02-travel.md의 모든 기능 ID를 넣고 매핑표를 주세요" |

### 화면 위에서 바로 지적하기

Claude Design은 시안의 특정 부분을 짚어서 의견을 남기거나 직접 고칠 수 있다. 말로 위치를 설명하기 어려우면 해당 부분을 선택하고 의견을 적는 쪽이 정확하다. 기능 이름은 버전에 따라 다를 수 있다.

### 알아 두면 편한 말

전문 용어를 몰라도 되지만, 아래 표현을 알면 원하는 것을 더 정확히 전달할 수 있다.

| 말 | 뜻 | 이렇게 쓴다 |
|---|---|---|
| 여백 | 요소 사이의 빈 공간 | "여백을 넉넉하게 해서 답답하지 않게" |
| 대비 | 글씨와 배경의 밝기 차이 | "대비가 약해서 글씨가 흐려 보여요" |
| 강조색 | 버튼처럼 눈에 띄어야 하는 곳에 쓰는 색 | "강조색은 한 가지만 써 주세요" |
| 톤 | 색과 분위기의 전체적인 느낌 | "톤을 좀 더 차분하게" |
| 위계 | 무엇이 먼저 눈에 들어오는지의 순서 | "제목보다 사진이 먼저 보이게 위계를 바꿔 주세요" |
| 밀도 | 한 화면에 들어간 정보의 양 | "밀도가 너무 높아요. 한 화면에 덜 담아 주세요" |
| 모서리 둥글기 | 상자 모서리가 둥근 정도 | "모서리를 덜 둥글게" |
| 상태 | 같은 화면의 여러 경우(불러오는 중, 빈 화면, 오류 등) | "이 화면의 모든 상태를 보여 주세요" |
| 다크 모드 | 어두운 배경 화면 | "다크 모드에서도 보여 주세요" |

### 대화가 길어졌을 때

대화가 아주 길어지면 앞에서 정한 내용이 흐려질 수 있다. 다음 경우에는 **새 대화를 시작**하는 것이 좋다.

- 단계 하나가 끝났을 때 (예: 2단계 확정 후 3단계 시작)
- 확정한 내용을 Claude Design이 자꾸 바꿀 때

새 대화에서는 처음처럼 파일을 다시 올리고, 아래처럼 시작한다.

```
00-brief.md를 먼저 읽어 주세요. 이전 대화에서 1~2단계를 확정했습니다. 확정 내용은 아래와 같습니다.
[결정 메모 붙여 넣기 / 브랜드 정리, 디자인 시스템 파일 첨부]
이 내용은 바꾸지 말고, 이번 대화에서는 3단계 대표 화면 중 "여행 상세"를 진행합니다.
```

### 막혔을 때

| 상황 | 해결 방법 |
|---|---|
| 같은 부분을 계속 고쳐도 마음에 안 든다 | 고치기를 멈추고 "완전히 다른 방향으로 3가지"를 요청한다. 또는 0단계 취향 자료에서 그 부분과 비슷한 예시를 찾아 보여 준다 |
| 뭐가 마음에 안 드는지 말로 못 하겠다 | "이 화면에서 개선할 점 5가지를 제안해 주세요"라고 물은 뒤 고른다 |
| 시안이 옛 디자인과 비슷해 보인다 | 옛 자료를 올리지 않았는지 확인한다. 0단계의 형용사와 예시를 다시 강조한다 |
| 기능이 빠지거나 바뀐 것 같다 | "해당 문서의 기능 ID 매핑표를 다시 만들고 빠진 ID를 알려 주세요"라고 요청한다 |
| 새 기능을 넣고 싶어진다 | 시안에 넣지 말고 메모해 두었다가 개발 담당과 상의한다 |
| 문서 내용 중 이해가 안 되는 기능이 있다 | 개발 담당에게 기능 ID로 물어본다 (예: "INS-19가 무슨 기능이에요?") |

## 5. 하면 안 되는 것

- 옛 서비스의 화면 캡처, 로고, 기존 디자인 문서를 Claude Design에 올리기
- 기능을 빼거나 새 기능 추가하기 (먼저 개발 담당과 상의)
- 화면 주소(URL) 바꾸기
- 실제 개인 정보가 담긴 사진이나 기록을 시안 데이터로 쓰기. 시안 데이터는 `08-content-samples.md`의 가상 데이터를 쓴다
- 다른 서비스의 디자인이나 로고를 그대로 베끼기

## 6. 개발 담당에게 넘기기

5단계 점검이 끝나면 아래를 개발 담당에게 전달한다.

| 전달할 것 | 설명 |
|---|---|
| HTML 프로토타입 1개 | 데스크톱과 휴대폰 화면이 모두 들어 있는 시안. Claude Design의 내보내기 기능으로 받는다 |
| 디자인 문서 | 색, 글꼴, 간격 같은 규칙(토큰) 표가 들어간 문서 |

| 보류 목록 | 넣고 싶었지만 기능 변경이라 보류한 아이디어 |

전달 방법(파일로 보낼지, Claude Design 프로젝트를 공유할지)은 개발 담당과 따로 정한다.

### 작성 원칙

- **무엇을 할 수 있는지만 쓰고, 어떻게 생겼는지는 쓰지 않는다.**
  - 색, 폰트, 배치, 컴포넌트 이름, CSS 클래스는 새 디자인이 정할 몫이다.
  - 예외는 지도와 달력처럼 형태 자체가 기능인 경우다.
- **브랜드 중립**: 옛 서비스 이름을 쓰지 않고 "서비스" 또는 `[서비스명]`이라고 쓴다.
- **사용자 문구는 "현재 문구"로 인용**한다. 표현은 바꿔도 되지만 의미는 보존해야 한다.
- **URL은 유지 대상**이다. 화면 구성은 자유롭게 바꿔도 되지만, 주소는 바꾸지 않는 것을 전제로 한다.
- 근거는 코드다. 코드로 확정하지 못한 것은 각 문서의 "확인 필요"에 모았다.
- `README.md`는 사람용이라 Claude Design에 넘기지 않는다. 기존 디자인 자료의 존재가 적혀 있어서, 넘기면 Claude Design이 그 자료를 요청할 수 있다.
