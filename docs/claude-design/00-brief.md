# 디자인 의뢰 브리프

이 문서는 함께 받은 자료를 읽는 출발점이다. 먼저 이 문서를 읽고, 아래 순서로 나머지 문서를 참고한다.

## 1. 의뢰 내용

로그인한 사용자만 쓰는 **개인 기록 웹 서비스**의 시각 디자인을 처음부터 새로 만든다.

- 서비스 이름과 브랜드는 새로 정한다. 새 브랜드 정보는 별도 브리프로 전달한다.
- 문서 안의 `[서비스명]`은 새 서비스 이름이 들어갈 자리다.
- 기존 디자인은 전달하지 않는다. 남길 것이 없으니 참고하지 않아도 된다.

서비스가 다루는 영역은 다음과 같다.

| 영역 | 사용자가 하는 일 |
|---|---|
| 홈 | 최근 기록과 다가오는 일정을 한눈에 보고 각 영역으로 이동한다 |
| 여행 | 여러 날에 걸친 여행을 일자별 장소, 사진, 태그로 기록하고 다시 본다 |
| 나들이 | 짧은 외출을 퀴즈를 풀어 열어 보는 방식으로 기록하고, 경로 지도를 본다 |
| 임장 | 부동산 현장 조사를 지역 → 회차 → 매물 단위로 계획하고 기록하고 비교한다. 지도에서 방문 순서와 도보 경로를 본다 |
| 달력 | 여러 캘린더의 일정을 월, 주 단위로 보고 관리한다 |
| 신발 | 오래 걷기 좋은 신발 추천을 둘러본다 |
| 프로필 | 내 정보와 화면 밝기 설정을 관리한다 |

## 2. 자유롭게 바꿔도 되는 것

- 브랜드: 로고, 색, 서체, 톤
- 정보 구조: 내비게이션 방식, 메뉴 묶음, 화면 배치
- 화면 단위: 한 화면을 여러 단계로 나누거나, 여러 화면을 하나로 합쳐도 된다
- 컴포넌트와 상호작용 방식
- 사용자 문구의 표현

## 3. 반드시 지킬 것

1. **기능을 빠뜨리지 않는다.** 기능 목록의 모든 기능 ID는 새 디자인 어딘가에서 수행할 수 있어야 한다.
2. **URL을 유지한다.** 화면 구성이 바뀌어도 기존 주소로 같은 기능에 도착해야 한다. 전체 URL 표는 `00-common.md`에 있다.
3. **문구의 의미를 보존한다.** 문서에 "현재 문구"로 인용한 안내, 오류, 확인 문구는 표현을 바꿔도 되지만 전달하는 의미는 같아야 한다.
4. **권한 차이를 반영한다.** 관리자만 쓰는 기능은 일반 사용자에게 보이지 않거나 쓸 수 없어야 한다.
5. **각 문서의 "기술 제약"을 따른다.** 예를 들어 지도 SDK가 바꿀 수 있는 범위, 달력 라이브러리의 한계, 업로드 제한이 있다.
6. **데스크톱과 모바일을 모두 설계한다.**
   - 데스크톱 1440px (`/main/...`), 모바일 390px (`/mobile/...`)
   - 두 기기는 별도 화면이지만 기능은 같다. 일부 화면은 한쪽에만 있다(문서의 "데스크톱/모바일 차이" 참고).
7. **화면 밝기 3종을 지원한다.** 시스템 설정 따르기, 밝게, 어둡게 (`COM-13`).
8. **접근성 기준**
   - WCAG 2.2 AA를 만족한다. 본문 대비 4.5:1, 포커스 표시와 비텍스트 요소 대비 3:1.
   - 키보드로 조작할 수 있어야 한다.
   - 한글 본문의 가독성을 우선한다.

## 4. 함께 받은 문서

| 파일 | 내용 |
|---|---|
| `00-common.md` | 앱 전역 기능: 로그인, 권한, 기기 판별, 내비게이션, 공통 상태 규칙, 전체 URL |
| `01-home.md` ~ `07-profile.md` | 영역별 기능 목록 |
| `04-inspection.md` + `04a` ~ `04d` | 임장 영역. 분량이 많아 여러 파일로 나뉘어 있다 |
| `08-content-samples.md` | 영역별 데이터 분량, 표기 형식, 샘플 레코드, 극단 케이스 |

### 기능 목록을 읽는 법

- 각 기능에는 `TRV-03` 같은 ID가 붙어 있다. 접두사는 영역을 뜻한다: `COM`, `AUTH`, `HOME`, `TRV`, `TRP`, `INS`, `CAL`, `SHO`, `PRF`. 번호 사이의 빈 구간은 일부러 비워 둔 것이다.
- 기능마다 다음 정보가 있다: 대상 사용자, 진입 경로, 흐름, 입력 항목, 표시 데이터, 상태, 결과, 정책, 기기 차이.
- **"상태"에 적힌 로딩, 빈 상태, 오류, 처리 중 같은 경우도 모두 디자인 대상이다.**
- 문서에는 생김새를 일부러 적지 않았다. 예외는 지도와 달력처럼 형태 자체가 기능인 경우다.
- **"확인 필요" 항목**은 아직 결정되지 않았거나 구현되지 않은 부분이다.
  - 디자인은 현재 동작을 기준으로 한다.
  - 더 나은 방식을 제안하고 싶다면, 별도 제안으로 구분해서 표시한다.
  - 정책상 위치만 정해진 미구현 기능은 디자인에 포함한다. 예: 여행 삭제는 수정 화면에 둔다(`TRV-09`).

### 콘텐츠 샘플을 쓰는 법

- 샘플은 모두 가상 데이터다. 시안에 그대로 써도 된다.
- 목업은 "보통" 샘플로 만든다.
- 데이터가 꽉 찬 경우와 빈약한 경우에도 화면이 깨지지 않는지 확인한다. 긴 한글 제목, 사진이 많거나 없는 기록, 일정이 몰린 날 등이 있다.

## 5. 진행 단계와 산출물

한 번에 전체를 만들지 않는다. 단계마다 검토를 받고 다음 단계로 넘어간다.

| 단계 | 산출물 |
|---|---|
| 1. 브랜드 | 로고(심볼, 글자를 합친 버전, 16px 파비콘, 어두운 배경용), 핵심 색, 톤 |
| 2. 디자인 시스템 | 토큰(색, 서체, 간격, 반경, 그림자, 움직임)을 밝게/어둡게 모두. 컴포넌트별 변형과 상태(기본, 호버, 포커스, 비활성, 오류, 로딩) |
| 3. 대표 화면 | 홈, 여행 상세, 임장 지역 상세(지도 포함), 임장 계획 등록, 달력 월 보기를 데스크톱과 모바일로 |
| 4. 전체 화면 | 나머지 모든 화면과 상태 |

공통 요구사항

- 3단계부터는 **기능 매핑표**를 함께 제출한다. 아래 형식을 따른다.
- 최종 산출물은 데스크톱과 모바일 화면을 모두 담은 **HTML 프로토타입 1개**와, 토큰 표가 들어간 **디자인 문서**다.

### 기능 매핑표 형식

| 기능 ID | 기능 | 화면(URL) | 수행하는 요소·위치 | 데스크톱 | 모바일 | 비고 |
|---|---|---|---|---|---|---|
| TRV-03 | 새 여행 등록 시작 | `/travel` | (예시) 목록 화면의 등록 진입점 | ✓ | ✓ | |
| INS-06 | 임장 계획하기 시작 / 질문 관리 진입 | `/inspection` | (예시) 지역 목록 화면의 진입점, 질문 관리는 관리자에게만 보임 | ✓ | ✓ | 질문 관리는 관리자 전용 |

- 해당 단계에 포함된 영역의 기능 ID는 빠짐없이 표에 들어가야 한다.
- 매핑되지 않은 기능 ID가 하나라도 있으면 그 단계는 완료로 보지 않는다.
- 한쪽 기기에서 의도적으로 제공하지 않는 기능은 비고에 이유를 적는다.
