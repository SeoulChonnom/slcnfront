# 임장 기록 — 화면 상세 디자인

요구사항 명세서: [`requirements_specification.md`](./requirements_specification.md)
동작 프로토타입: [`design/prototype.html`](./design/prototype.html) · 캡처: [`design/screens/`](./design/screens/) (`<화면>-desktop.webp` 1440px · `<화면>-mobile.webp` 390px 전체 · `<화면>-mobile-top.webp` 390px 첫 화면)

이 문서는 명세서(도메인·데이터 규칙)를 화면으로 옮긴 설계다. 데이터 모델은 명세서가
기준이고, 이 문서는 **무엇을 어디에 어떻게 보여 주고 어떤 상태를 가지는가**만 정한다.

**확정된 것** — 목록 단위(지역), 회차 처리(레일 + `?visit=` 딥링크), 매물의 회차 간 자동 연결,
라우터 세그먼트(`/inspection`), 화면 구성과 상태 전부.
**열려 있는 것** — §10의 다섯 가지. 모두 구현을 막지는 않고, 현재 전제를 각 항목에 적어 뒀다.

## 1. 명세서 분석 — 화면으로 옮길 때 갈렸던 지점

명세서는 데이터가 촘촘한 대신 화면 기준이 두 군데 비어 있었다. 아래는 확인 후 확정한 내용이다.

### 1.1 계층이 4.5단계다

```
InspectionArea (성수동)
  └ InspectionVisit (3차 · 2026.09.17 14:00)      ← 지역 전체 평가·사진·태그
      └ [단지/건물명 그룹]  (트리마제)              ← §41. Entity 아님, 표시용 그룹
          └ ViewedProperty (101동 1203호 / 84A)    ← 관심도·태그·장단점·사진
              └ PropertyAnswer                     ← QuestionVersion 고정
```

`complexName`이 Entity가 아니라 문자열(§13·§45)이므로 **단지는 화면에서만 존재하는 그룹**이다.
지역 상세의 매물 목록은 `complexName` 기준으로 묶어 소제목 + 매물 행으로 그린다.
단지 자체를 누를 수 있는 페이지는 만들지 않는다 — 누를 게 없는 링크가 생기기 때문이다.

### 1.2 목록 단위 — 명세 §38과 요청이 달랐다

명세 §38의 "임장 목록"은 **임장(회차) 단위**이고, 요청은 **지역 단위**였다. → **지역 단위로 확정.**
한 행 = 한 지역이고, 요약값은 최신 회차에서 끌어온다. 같은 지역이 목록에 여러 번 뜨지 않고,
"어디를 몇 번 걸었나"가 목록의 1급 정보가 된다. §38이 요구한 일곱 항목은 모두 이 행 안에 있다.

| §38 요구 | 지역 행에서 |
| --- | --- |
| 임장 지역 | 지역명 + 지역 설명 |
| 임장일 | 최근 임장 일시 + 첫 임장일 |
| 한줄평 | 최신 회차 한줄평 |
| 재방문 의사 | 최신 회차 값 |
| 확인한 매물 수 | 지역 누적 매물 수 |
| 가장 관심도 높은 매물 | 지역 전체 1위(단지명 + 매물명 + 관심도) |
| 태그 | 최신 회차 태그 상위 3개 + `+N` |

### 1.3 회차 처리 — 별도 페이지를 만들지 않는다

지역 상세 안에 **회차 레일**을 두고, 레일을 고르면 아래 기록 전체가 바뀐다.
화면은 3개로 유지되고 회차는 URL 파라미터(`?visit=`)로 남아 특정 회차 직행이 된다.
명세 §39의 "임장 상세 화면" 요구 항목은 전부 이 패널 안에 있다.

### 1.4 매물의 회차 간 연결 — 자동 연결

데이터상 `ViewedProperty`는 회차에 종속되어 재방문해도 별개 레코드다(§49-3).
화면에서는 **같은 지역 안에서 `complexName` + `매물명`이 일치하면** 같은 매물로 보고 묶는다.

- 비교 규칙: 앞뒤 공백 제거 + 연속 공백 1칸으로 정규화 후 정확 일치. 유사도 매칭은 쓰지 않는다.
- 프런트 그룹핑이므로 백엔드 스키마 변경이 없다.
- 오탐 가능성이 있으므로 문구를 단정하지 않는다 — "같은 이름으로 기록된 다른 회차",
  그리고 **연결 해제**를 항상 옆에 둔다.
- 얻는 것: `6월 ★3 → 9월 ★5, 2단계 올림`. 이 서비스에서만 나오는 정보다.

## 2. 라우터 — 확정

세그먼트는 **`inspection`** 으로 확정한다. 기존 `route-manifest.tsx`의 평면 구조와
`/main` `/mobile` 접두사 규칙을 그대로 따른다.

| 화면 | 경로 | 파라미터 |
| --- | --- | --- |
| 지역 리스트 | `/{device}/inspection` | `?q=` `?revisit=` `?sort=` |
| 지역 상세 | `/{device}/inspection/:areaId` | `?visit=:visitId` (없으면 최신 회차) |
| 매물 상세 | `/{device}/inspection/:areaId/property/:propertyId` | — |
| 임장 작성 | `/{device}/inspection/register` | `?draft=:visitId` 로 DRAFT 이어쓰기 |
| 임장 수정 | `/{device}/inspection/:areaId/visit/:visitId/edit` | 작성과 같은 마법사, 3단계 진입 |
| 매물 편집 | `/{device}/inspection/:areaId/visit/:visitId/property/:propertyId/edit` | 신규는 `.../property/new` |
| 질문 관리 | `/{device}/inspection/questions` | 관리자 전용 |

`{device}`는 `main` 또는 `mobile`. 도메인 모듈은 `src/domains/inspection/`에 둔다.

### 매물 상세에 `:areaId`를 남기는 이유

`/inspection/property/:propertyId`(지역 없이)로도 되고 더 짧다. 그래도 지역을 남긴다 —
매물 상세는 breadcrumb(`임장 › 성수동 › 2026.09.17 임장 › 트리마제 101동 1203호`),
이전/다음 매물, 회차 간 연결을 모두 **지역 문맥 위에서** 그린다. 지역이 URL에 없으면
그 세 가지가 전부 추가 조회가 되고, 새로고침이나 링크 직행에서 한 박자 늦는다.

### 매니페스트에 넣을 때

`BASE_PROTECTED_ROUTES`에 아래를 더하고, `RoutePageKey`에 7개 키를 추가한다.

```ts
{ path: 'inspection', page: 'inspectionAreaList' },
{ path: 'inspection/register', page: 'inspectionRegister' },
{ path: 'inspection/questions', page: 'inspectionQuestions' },
{ path: 'inspection/:areaId', page: 'inspectionAreaDetail' },
{ path: 'inspection/:areaId/property/:propertyId', page: 'inspectionPropertyDetail' },
{ path: 'inspection/:areaId/visit/:visitId/edit', page: 'inspectionVisitEdit' },
{ path: 'inspection/:areaId/visit/:visitId/property/:propertyId/edit', page: 'inspectionPropertyEdit' },
```

주의할 점 하나. 매니페스트 맨 끝에 `{ path: ':brand/:shoesName', page: 'shoeDetail' }`라는
두 칸짜리 와일드카드가 이미 있다. React Router는 고정 세그먼트를 동적 세그먼트보다 높게 매기므로
`inspection/:areaId`가 이긴다. 배열 순서와 무관하게 이기지만, 알고 넣어야 한다.
`inspection/register` `inspection/questions`도 같은 이유로 `inspection/:areaId`보다 먼저 매칭된다.

`withShell(BASE_PROTECTED_ROUTES, {}, 'main')`을 그대로 쓰면 7개 모두 기본 셸에 붙는다.
별도 셸이 필요한 화면은 없다.

## 3. 시각 언어 — 무엇을 상속하고 무엇을 바꾸는가

기존 `DESIGN.md`(Seoul Quiet Editorial)를 **그대로 상속한다.** 새 색·새 폰트·새 그림자는 없다.

상속: 따뜻한 종이 `--color-canvas` 바탕, Seoul Pink는 동작·선택에만, 잉크 블랙 타이포,
Pretendard 단일 패밀리, 6/8/12/18/24/pill 라운드 문법, 글래스는 내비게이션 크롬 전용,
포커스 링은 `--color-focus-ring`(분홍 아님).

이 도메인에서 조정하는 것은 **두 가지뿐**이다.

| 항목 | 다이어리(기존) | 임장(이번) | 이유 |
| --- | --- | --- | --- |
| 기본 컨테이너 | 카드(`--radius-lg` + 헤어라인) | **헤어라인 罫선 행** | 한 화면에서 비교·훑기를 해야 하는 Operate 화면이다. 카드는 항목마다 액자를 씌워 비교를 방해한다 |
| 세로 리듬 | 섹션 80 / 히어로 112px | **블록 40 / 구간 56px** | 사진이 아니라 판단 근거가 주인공이라 밀도를 올린다. `--fr-block`, `--fr-block-lg` 두 값으로만 관리 |

추가 토큰은 이 셋뿐이다.

```css
--fr-block: 2.5rem;     /* 40px */
--fr-block-lg: 3.5rem;  /* 56px */
--fr-measure: 42rem;    /* 672px, 임장/매물 메모 본문 측정폭 */
```

## 4. 이 도메인에서 새로 생기는 표시 요소

### 4.1 재방문 의사 (`YES` / `MAYBE` / `NO`)

```
✓ 다시 임장하고 싶음     success  #15794F
! 조금 더 고민           warning  #955B0A
⊘ 재방문하지 않을 예정    body-muted #6F666A
```

- **`NO`에 error 빨강을 쓰지 않는다.** 빨강은 삭제·실패에만 남긴다. "안 갈 예정"은 오류가 아니다.
- 색만으로 뜻하지 않는다(DESIGN.md §13). 항상 **아이콘 + 글자**가 함께 간다.
  회차 레일처럼 아이콘만 보이는 자리에는 `sr-only` 글자를 붙인다.
- 지역 리스트에서는 글자형, 회차 패널 머리에서는 테두리 pill형.

### 4.2 관심도 (1~5)

- 유니코드 `★`이 아니라 **그린 SVG 별**. 아이콘은 그려서 쓴다.
- 칠한 별 `--color-accent-muted`(#A34F6D). Seoul Pink는 흰 바탕에서 1.91:1이라
  뜻을 지닌 그래픽으로 쓸 수 없다.
- **항상 숫자를 옆에 둔다**(`★★★★☆ 4`). 상세에서는 `4 / 5 · 관심 있음`까지.
- 스크린리더: `관심도 5점 만점에 4점`.
- 입력형은 44×44 터치 타깃 5개 + `role="radiogroup"`.

### 4.3 상태 — 완료는 표시하지 않는다

`COMPLETED`는 아무 배지도 붙이지 않는다. `DRAFT`만 **점선 테두리 + 연회색 "작성 중"** 배지를
받는다. 아카이브는 조용해야 하고, 손댈 게 남은 것만 눈에 띄면 된다.
DRAFT 행에는 이유를 한 줄로 붙인다 — `필수 문답 2개 남음 — 관리비 수준, 주차 대수`.

### 4.4 회차 도트 (지역 리스트)

행 왼쪽 레일에 `3회` + 도트 N개(최신 하나만 분홍) + `최근 09.17`.
장식이 아니라 **몇 번 걸었는지**를 세는 정보다. 리스트를 훑을 때 지역의 무게가 바로 읽힌다.

### 4.5 회차 레일 (지역 상세) — 이 화면의 서명 요소

가로 스크롤 탭 줄. 각 항목은 `3차 · 가장 최근` / `2026.09.17` / `목 14:00 · 매물 3` + 재방문 마크.
선택 항목만 잉크색 + 아래 2px 밑줄. 나머지는 muted. 회차 사이는 세로 헤어라인.
모바일에서는 화면 밖으로 이어져 다음 항목이 살짝 보이도록 둔다.

### 4.6 회차 연결 스트립 (매물 상세)

`--color-surface-muted` 패널, 최대폭 46rem. 머리줄 오른쪽에 **연결 해제**.
각 행: 날짜 · 관심도 · 변화량(`↑ 2단계 올림` / `↓` / `— 처음 본 회차`). 현재 보는 회차는 점선.

## 5. 화면 상세

### 5.1 임장 지역 리스트

**목적** — "어디를 몇 번 걸었고, 지금 가장 마음에 있는 집이 어디인지"를 첫 화면에서 읽는다.

**데스크톱 구성** (최대 77.5rem)

```
제목 "임장" + 요약 한 줄 ("6개 지역을 10번 걸었고, 매물 17건을 봤습니다.")   [임장 기록하기]
검색 필드 (pill, 52px)
필터 칩: 전체 N / 다시 임장하고 싶음 N / 조금 더 고민 N / 재방문하지 않을 예정 N     [최근 임장순 ▾]
──────────────────────────────────────────────────────────
[회차도트]  지역명 + 지역 설명        재방문 의사            최고 관심 매물
            "최신 한줄평"             최근 임장 일시          단지명
            태그 칩 3 + N             누적 매물 · 첫 임장     매물명 + ★N
                                                            사진 썸네일 2 + N
──────────────────────────────────────────────────────────
```

그리드 `5.5rem / 1fr / 15rem / 10.5rem`, 행 패딩 24px, 행 사이는 헤더라인 1px.
호버는 `--color-stripe-highlight` 바탕만 바꾼다 — 카드가 뜨지 않는다(DESIGN.md §6).

**모바일 구성** — 2열(회차 레일 4.25rem + 본문)로 접고, 메타·최고 관심 매물·썸네일은
본문 열 아래로 내려 쌓는다. 상단 "임장 기록하기" 버튼은 **감춘다** — 하단 FAB 하나만 남긴다.

**요약값이 어디서 오는가** (백엔드 협의 필요, §7 참고)

| 표시 | 출처 |
| --- | --- |
| 임장 N회 | 지역의 `InspectionVisit` 수 (DRAFT 포함) |
| 최근 임장 | 가장 큰 `visitedAt` |
| 누적 매물 | 지역 전체 `ViewedProperty` 수 |
| 최신 한줄평 / 재방문 의사 / 태그 | 최신 회차 값 |
| 최고 관심 매물 | 지역 전체에서 `interest` 최대. 동점이면 최신 회차 우선 |
| 썸네일 | 최신 회차 `InspectionVisitImage` 앞 2장 + 지역 전체 장수 |

**작성 중 지역** — 최신 회차가 DRAFT면 지역명 옆에 "작성 중" 배지, 한줄평 자리에는
`한줄평을 아직 쓰지 않았습니다.`(muted), 메타에 `필수 문답 3개 미작성`.

### 5.2 지역 상세

**목적** — 한 지역의 판단이 회차를 거치며 어떻게 변했는지 본다.

```
임장 › 성수동
성수동                                        [지역 정보 수정]  [+ 이 지역 다시 임장]
서울숲 ~ 뚝섬역 주변 · 임장 3회 · 누적 매물 4건 · 첫 임장 2026.03.11
──────────────────────────────────────────────────────────
● 3차·가장 최근 2026.09.17   │ 2차 2026.06.02   │ 1차·처음 2026.03.11
  목 14:00 · 매물 3 ✓        │ 화 11:00 · 매물 1 !│ 수 18:30 · 매물 없음 ✓
──────────────────────────────────────────────────────────
```

### 5.4 작성 플로우

명세 §35의 흐름을 3단계 + 매물 편집 + 완료 검증으로 옮긴다.
단계 표시는 기존 `TripRegisterWizard`(DESIGN.md §15.4)와 같은 문법을 쓴다.
컬럼은 50rem로 묶어 가운데 정렬한다 — 한 줄 입력이 1440px에 늘어나면 미완성 페이지로 읽힌다.

#### ① 지역

- 검색 입력 → 기존 지역 결과 행(지역 설명·임장 N회·최근일 + `4번째 회차로 기록` 칩)
- 결과 아래 점선 블록에 **새 지역 만들기**(지역명 필수 + 지역 설명 선택)
- 지역을 고르기 전에는 "다음" 비활성 + 이유 한 줄

#### ② 임장 기본 정보

필수는 **임장 일시**와 **재방문 의사** 둘뿐이다(§36). 나머지는 나중에 채워도 된다고 화면에 적는다.

날짜 + 시각 / 재방문 의사(3 라디오 pill) / 한줄평 / 전체 메모 / 장점 · 단점 /
태그(입력 + 자주 쓴 태그 제안) / 임장 사진 드롭존.
사진 썸네일은 **드래그 핸들 + 캡션 입력 + 삭제**를 모두 갖는다(§30·§32의 `sortOrder`).
상단에 `14:22에 임시 저장됨` 자동 저장 표시.

#### ③ 확인 매물

- 매물 행: 드래그 핸들 · `단지 · 매물명` · 상태 · 관심도 · [수정/이어서 쓰기]
- DRAFT 행은 **남은 것을 문장으로** 적는다: `필수 문답 2개 남음 — 관리비 수준, 주차 대수`
- "작성 중" 배지는 이름 줄이 아니라 **사유 줄**에 붙는다. 이름 줄에 두면 배지가 이름과 폭을
  다투어 `트리마제 · 102동 1501호 / 84A`가 꺾인다
- 모바일에서는 이름이 **전체 폭 한 줄**을 차지하고, 관심도와 버튼이 그 아래 줄에 나란히 선다.
  행마다 그리드가 따로라 버튼 라벨이 길면(「이어서 쓰기」 94px vs 「수정」 54px) 이름 칸이
  같은 화면 안에서 행마다 달라진다
- `[+ 매물 추가]`, 그리고 매물 없이도 완료 가능함을 명시
- 질문 고정 안내(§24): `이 임장에서 쓰는 질문은 작성을 시작한 2026.09.24 14:22 시점 구성으로
  고정됐습니다. 지금 질문이 바뀌어도 이 임장에는 반영되지 않습니다.`

#### ③-1 매물 편집

단지/건물명(이 임장·지역에서 쓴 이름 자동완성) · 매물명 · **관심도(필수)** · 한줄평 · 메모 ·
장단점 · 태그 · 사진 → 그 아래 **문답**을 타입별 컨트롤로 렌더.
미작성 필수 항목은 필드 아래 warning 한 줄.
하단: `[매물 삭제]` … `[작성 중으로 저장]` `[매물 완료]`(조건 미충족 시 비활성 + 사유 배너).

단지명 필드 힌트에 연결 규칙을 적는다 — `같은 이름이어야 회차 간 매물이 연결됩니다.`

#### ④ 완료 검증

§36의 조건을 그대로 체크리스트로 보여 준다. 통과는 ✓, 막힌 항목은 ⚠ + **무엇이 왜 막혔는지**.

```
✓ 임장 지역이 정해졌습니다              성수동
✓ 임장 일시가 입력됐습니다              2026.09.24 14:00
✓ 재방문 의사가 입력됐습니다            다시 임장하고 싶음
⚠ 매물 2건이 아직 작성 중입니다
    102동 1501호 — 주차 대수, 관리비 수준 미작성
    105동 803호 — 관심도와 필수 문답 5개 미작성
```

그리고 **선택지를 두 개 준다**: 「남은 두 매물을 마저 쓰기」 / 「두 매물을 이 임장에서 빼고 완료하기」.
막다른 오류 화면으로 끝내지 않는다.

```

이미 저장된 답변은 그대로 남습니다.
      질문                                  타입      필수   사용
⠿  거실 및 방의 채광은 어떤가?              긴 글     필수   ● 사용중   [수정]
   v2 · 답변 12건 · 마지막 수정 2026.05.02
   버전 기록
     v2  거실 및 방의 채광은 어떤가?   2026.05.02 · 답변 7건
     v1  거실 채광은 어떤가?          2026.01.08 · 답변 5건
⠿  …
⠿  반려동물을 키울 수 있는가?  (미사용 행: surface-muted 바탕, 본문 weight 400)
```

- **삭제 버튼이 없다**(§34.4). 있는 것은 미사용 토글뿐이고, 그 결과를 문장으로 적는다.
- 수정은 **모달**로 연다(DESIGN.md §8.10). 목록에서 어떤 질문을 고르는지가 맥락이므로
  목록을 떠나지 않고, 저장·취소가 끝나면 원래 행으로 돌아온다. 데스크톱은 가운데 정렬
  다이얼로그(최대 34rem, 24px 라운드, 흐린 스크림), 모바일은 **위쪽만 둥근 바텀 시트**.
  Esc·스크림·닫기 버튼으로 닫히고, 포커스는 열릴 때 첫 입력으로 들어가 닫히면 부른 행으로 돌아간다.
  바닥은 `취소 | v3으로 저장` 한 줄 + `미사용 처리`를 그 아래 조용한 줄로 나눈다.
- 수정 패널은 저장 전에 결과를 먼저 말한다:
  `질문 문장을 고치면 v3이 새로 생깁니다. 이미 저장된 답변 12건은 각자 답할 때의 문장(v1·v2)을
  그대로 보여 줍니다.` 저장 버튼 라벨도 `v3으로 저장`이다.
- 답변이 있는 질문은 **타입 변경 불가** — 필드 아래 이유를 적는다.
- 각 행에 답변 건수를 항상 보여 준다. 미사용/수정의 파급을 숫자로 알고 누르게 한다.
- 모바일: 타입·필수·사용은 질문 아래로 접어 쌓는다.

## 8. 접근성 · 반응형 · 모션

- 포커스 링은 전역 `--color-focus-ring`(#A34F6D). 분홍은 3:1을 못 넘어 쓰지 않는다.
- 색 단독 의미 금지: 재방문 의사·관심도·상태 모두 글자 또는 숫자를 동반한다.
- 터치 타깃 44px. 별점 입력 버튼 5개도 44×44.
- 사진에는 캡션이 곧 대체 텍스트. 캡션이 없으면 `alt=""`로 둔다.
- 회차 레일은 `role="tablist"` + 좌우 화살표 이동, 패널은 `?visit=`과 동기.
- 반응형 경계는 833px(DESIGN.md §12의 태블릿/소형 데스크톱 경계).
  1440 / 390 양쪽에서 가로 스크롤 0px 확인.
- 모션은 160/240ms, `cubic-bezier(0.2,0,0,1)`. 회차 전환은 페이드만. 카드 리프트 없음.
  `prefers-reduced-motion`에서 전부 정지.

### 모바일 컨트롤 치수 (390px 실측)

데스크톱 값을 그대로 쓰면 390px에서 입력이 52~54px, 버튼이 46px + 좌우 22px로 화면을 과하게
먹는다. 기준점 두 개 사이로 조였다 — **44px(터치 최소)** 와 **48px(앱의 `.slcn-field__control`,
`.slcn-button[data-size="md"]`)**.

| 요소 | 조정 전 | 조정 후 | 근거 |
| --- | --- | --- | --- |
| `.fr-input` `.fr-select` | 52~54px | **48px** | 앱의 필드 높이와 일치 |
| `.fr-textarea` | 120 / 96px | **88 / 78px** | 작성 2단계에 텍스트영역이 5개다. 원래 높이면 한 화면에 한 개도 안 들어온다 |
| `.fr-search input` | 48px / 좌우 48px | **46px / 42px** | 검색은 필드보다 가벼워야 한다 |
| `.fr-btn` | 46px / 좌우 22px | **44px / 18px** | 터치 최소치에 딱 맞춘 값. 이보다 줄이면 기준 위반 |
| `.fr-chip` | 37px | **33px** | 정적 메타데이터다. 버튼과 비슷한 크기로 보이면 안 된다 |
| `.fr-thumb input`(캡션) | 27px | **36px** | 27px는 손가락으로 집기 어렵다 |

**반대 방향 문제도 있었다.** 작은 버튼(`.fr-btn--sm` 37px), 필터 칩(`.fr-filter` 39px),
스위치 라벨(20px), 빵부스러기 링크(21px)가 44px에 미달했다. 보이는 크기를 키우는 대신
`::after` 오버레이로 **히트 영역만 44×44로** 넓혔다. 시각적 위계는 그대로 두고 손가락만 맞춘다.

라벨이 긴 라디오 묶음(재방문 의사)은 모바일에서 **세로로 쌓는다**. 가로로 늘어놓으면 줄마다
길이가 달라 눈이 왼쪽 정렬을 잡지 못한다. `예/아니오`, `필수/선택`처럼 짧은 묶음은 가로를 유지한다.

모바일 필터 줄은 감싸지 않고 **한 줄 가로 스크롤**로 둔다. 3행으로 접히면 첫 기록이
첫 화면 밖으로 밀려난다.

## 9. 백엔드에 필요한 것 (협의 필요)

화면이 성립하려면 아래가 필요하다. 명세서에 없던 **집계**가 대부분이다.

1. **지역 목록 응답의 집계 필드** — `visitCount`, `lastVisitedAt`, `firstVisitedAt`,
   `totalPropertyCount`, `latestVisit{ oneLiner, revisitIntent, tags, status }`,
   `topProperty{ complexName, propertyName, interest }`, `thumbnails[0..1]`, `totalImageCount`.
   프런트에서 전체를 받아 계산하면 목록 한 번에 모든 회차·매물을 끌어와야 한다.
2. **DRAFT 미완료 요약** — 지역 행과 매물 행에 `필수 문답 N개 남음`을 적으려면
   미충족 필수 질문의 **개수와 이름**이 필요하다.
3. **지역 상세 한 번 호출** — 회차 목록(요약) + 선택 회차 상세 + 매물(문답 포함)을
   한 번에 받으면 회차 전환이 즉시 된다. 회차 수가 많아지면 선택 회차만 지연 로딩.
4. **문답 응답에 질문 메타 동봉** — 각 `PropertyAnswer`에 그때의 `questionText`,
   `version`, `type`, `required`, `isCurrentVersion`, `questionEnabled`.
   이게 없으면 과거 기록을 정확히 복원할 수 없다(§20).
5. **질문 관리 응답에 답변 건수** — 질문별/버전별 `answerCount`.
6. **정렬 값 저장 엔드포인트** — 매물·사진 `sortOrder` 일괄 갱신(§32·§33).

회차 간 매물 연결은 **프런트에서 계산**하므로 백엔드 변경이 필요 없다.
다만 §43(매물 비교)로 갈 때는 명시적 연결 컬럼을 두는 편이 낫다.

## 10. 남은 결정 사항

1. **지역 정보 수정 시 과거 기록** — 명세 §6은 "독립 유지"라고만 한다. 지역명을 바꾸면
   과거 회차의 헤더 지역명도 새 이름으로 보이는가, 당시 이름을 보존해 보여 주는가.
   (현재 설계는 **새 이름으로 통일**을 전제했다.)
2. **매물 자동 연결 범위** — 지금은 같은 지역 안에서만 묶는다. 지역이 달라도 단지명이
   같으면(예: 성수동 / 성수동2가에 걸친 단지) 묶을지.
3. **목록 페이지네이션** — 지역 수가 적을 것으로 보아 전체 로드를 전제했다.
   회차·매물이 쌓였을 때 더보기를 넣을 기준.
4. **질문 관리 접근 권한** — 두 사용자 모두 들어갈 수 있는가, 한 명만인가.
   (지금은 `/{device}/inspection/questions`를 일반 메뉴에 노출하지 않고 직접 진입만 전제했다.)
5. **임장 사진 캡션 필수 여부** — 매물 사진은 캡션이 비교에 쓰이므로 권장,
   임장 사진은 선택으로 뒀다. 반대로 갈지.

## 11. 검증 결과

이번 세션에서 실제로 확인한 것과 하지 않은 것.

**확인함**

- Pretendard 400·600이 실제로 로드됨 — `document.fonts.check('400 15px Pretendard')`,
  `check('600 15px Pretendard')` 모두 `true`. 선언만 보고 판단하지 않았다.
- 1440px / 390px 양쪽에서 `scrollWidth - clientWidth === 0` (가로 스크롤 없음).
- 10개 화면 × 2 디바이스 전체 캡처 후 육안 검수 2라운드.
  1라운드에서 찾은 결함(아이콘 크기 규칙 누락으로 SVG가 300×150으로 펼쳐짐,
  최고 관심 매물 열 줄바꿈 붕괴, 메타 문장이 단어 중간에서 접힘, 질문 관리 버튼 세로 쪼개짐,
  모바일 추가 버튼 중복)을 일괄 수정하고 2라운드에서 해소 확인.
- 390px 실뷰포트에서 모든 인터랙티브 요소의 실측 치수를 뽑아 44px 기준으로 감사했다.
  남은 미달은 **본문 인라인 텍스트 링크(37px)** 와 **사진 캡션 입력(36px)** 뿐이다.
  둘 다 WCAG 2.5.8(AA)의 24px 최소는 넘고, 인라인 링크는 규정상 예외다.
- FAB가 작성 마법사 화면에도 떠서 본문을 가리던 것을 찾아, 조회 화면(목록·지역·매물)에만 남겼다.
- 캡처 브라우저를 `--lang=ko-KR` 로 띄우고 컨텍스트 로케일도 `ko-KR`/`Asia/Seoul`로 고정했다.
  (컨텍스트 로케일만으로는 부족했다 — 날짜·시각 입력의 표기 형식은 브라우저 UI 언어를 따른다.)
  지금은 `2026. 09. 24.` / `오후 02:00` 로 렌더된다.

- 모바일 전체 캡처는 고정 탭바·FAB를 감추고 찍었다(고정 요소가 본문 위에 겹쳐 찍히는
  캡처 특성 때문). 크롬이 포함된 첫 화면은 `*-mobile-top.webp`로 따로 있다.

**확인하지 않음**

- 실제 앱(`src/`)에는 아무것도 반영하지 않았다. 구현은 이번 범위가 아니다.
- 실사진이 없어 갤러리·썸네일은 자리와 캡션만 잡은 플레이스홀더다.
- 다크 테마 렌더링. 토큰만 상속했을 뿐 이 화면들을 다크로 캡처하지 않았다.
- 키보드 탭 순서와 스크린리더 읽기는 마크업 수준에서만 설계했고 실기기 검증은 하지 않았다.
- 데이터는 전부 데모다. 실제 기록이 아니다.
