# 나들이 등록 위저드 — Accessibility Audit

Scope: `/main/map/register` (1440×900) and `/mobile/map/register` (390×844), light + dark.
All measurements re-taken against the **committed** tree (`420180c`) after an agent-made
commit (`020b29f`) was reverted — the first focus-ring pass was measured against that
contaminated tree and its `.slcn-field__control:has(...)` results were discarded.

---

## Findings

### [P1] All three file dropzones have no visible focus indicator
- **Location**: `src/components/ui/FileDropzone.tsx` (the `<input type="file" class="slcn-file-dropzone__input">`), styled by `src/styles/components-common.css` `.slcn-file-dropzone__input`. Affects 로고 이미지, 지도 1, 지도 2.
- **Impact**: A keyboard user tabbing through the form reaches each dropzone and sees **nothing at all** change on screen. The control is operable (Enter/Space opens the picker), but there is no way to know it has focus, so the user loses their place in a 3-step form whose primary inputs are these dropzones.
- **WCAG**: 2.4.7 Focus Visible (Level AA) — failure.
- **Evidence**: The focusable element is the input, measured `1×1 px` with `clip: rect(0px, 0px, 0px, 0px)`. It does receive `outline: rgb(163, 79, 109) solid 2px` and matches `:focus-visible` — but `clip` removes the outline from the rendered output along with the box. The visible drop target `.slcn-file-dropzone__label` measures `1146×150` and computes `outline: rgb(27, 27, 27) none 3px` (i.e. `outline-style: none`) and `box-shadow: none` while the input is focused.
- **Recommendation**: Style the visible label from the input's focus state, e.g.
  `.slcn-file-dropzone:has(> .slcn-file-dropzone__input:focus-visible) .slcn-file-dropzone__label { outline: 2px solid var(--color-focus-ring); outline-offset: 2px; }`.
  This is the same shape as the (reverted) `020b29f` patch, which solved the equivalent problem for `.slcn-field__control` but never covered the dropzone.

### [P2] Radio focus ring draws on the 20×20 native input, not the clickable pill
- **Location**: `src/components/ui/RadioGroup.tsx` `.slcn-radio-group__option input`; wizard styling at `src/styles/components-common.css` `.slcn-trip-register-wizard .slcn-radio-group--inline .slcn-radio-group__option`.
- **Impact**: The whole pill is the click target and the whole pill is what reads as "the control", but the focus ring outlines only the small circle inside it. On desktop the indicator covers roughly 3.5% of the target's area, so at a glance the selected 유형 pill and the focused one are hard to tell apart.
- **WCAG**: 2.4.7 Focus Visible passes (an indicator does exist). 2.4.11 Focus Appearance (2.2, AA) is not met — the indicator does not cover the control it indicates.
- **Evidence**: focused radio input measures `20×20` with `outline: rgb(163, 79, 109) solid 2px`; its wrapping `label.slcn-radio-group__option` measures `567×55` (desktop, 1440px) / `146×54.5` (mobile, 390px) and draws no outline and no box-shadow.
- **Recommendation**: Move the ring to the label with `:has(input:focus-visible)`, matching the dropzone fix above so both primitives use one pattern.
- **Note**: This was already reported as P3 in the 2026-08-31 critique and is still open; the hardening pass did not touch it.

### [P3] 유형 radio group's required state is not exposed programmatically
- **Location**: `src/components/ui/RadioGroup.tsx` — the `required` prop renders only `<span aria-hidden='true'> *</span>`; no `aria-required` reaches the `role="radiogroup"`.
- **Impact**: Sighted users see the `*`; screen-reader users are told nothing until submission fails. Every other required control on this surface carries the native `required` attribute.
- **WCAG**: 3.3.2 Labels or Instructions (A) — weak; the group is announced as invalid on error via `aria-invalid`, so this is a gap rather than a failure.
- **Evidence**: DOM probe of required inputs on step 1 returned exactly three (`date`, `나들이 이름`, `로고 이미지` file input); neither radio carries `required`, and the radiogroup has no `aria-required`.
- **Recommendation**: Set `aria-required="true"` on the element carrying `role="radiogroup"` when `required` is passed.

### [P3] Modal close control uses a `✕` text glyph instead of a drawn icon
- **Location**: `src/components/ui/Modal.tsx` (rendered inside `ConfirmDialog`, reached from the wizard's 취소 action).
- **Impact**: The accessible name comes from `aria-label`, so this is not a naming defect — but the glyph is read by some screen readers as "multiplication sign" if the label is ever removed, and it renders in the body font rather than matching the app's SVG icon set (the dropzone clear button beside it is a real SVG).
- **Evidence**: focus-trap probe captured the dialog's three tab stops as `나가기`, `✕`, `계속 쓸게요`.
- **Recommendation**: Replace with the same 2-path SVG used by `.slcn-file-dropzone__clear`.

### [P3] axe `image-redundant-alt` on the desktop header logo
- **Location**: `src/components/layout/DesktopHeader.tsx` — `<img alt="SLCN" class="slcn-desktop-header__logo">` adjacent to the "SLCN" wordmark text.
- **Impact**: Screen readers announce "SLCN" twice in the header. Outside the wizard, present on every `/main/*` route; pre-existing, not introduced by the hardening pass.
- **WCAG**: 1.1.1 Non-text Content (A) — advisory; axe rates it `minor`.
- **Evidence**: the only axe violation found in the entire run (desktop light + dark, dialog state). Mobile returned zero violations in every state.
- **Recommendation**: `alt=""` on the logo image, since the adjacent text already names the brand.

### Cross-reference
The 200%/150% text-reflow failure (WCAG **1.4.4 Resize Text**, **1.4.10 Reflow**, both AA) is a
genuine accessibility failure but is scored under **Responsive Design** per the audit rubric,
which owns "text scaling". It is the single most serious accessibility problem on this surface.
Independently reproduced: at 390px the document grows to `scrollWidth 504` (150%) and `668` (200%)
against `clientWidth 390`.

## Verified working

- **axe-core: zero violations inside the wizard.** Seven states (step 1 empty, step 1 all-errors, step 2, step 2 + 2번 지도, step 3, step 3 all-errors, 취소 dialog open) × desktop/mobile × light/dark. The only hit in the whole matrix is the header-logo `image-redundant-alt` above, which is shell chrome.
- **Contrast passes AA everywhere measured, in both themes.** 15 captured text/background pairs plus placeholder text, recomputed from raw values: light 4.63–17.22:1, dark 5.74–16.65:1. Tightest pair is the completed-step pill at 4.63:1 light (threshold 4.5). Placeholder text — a common failure point — measures 5.55:1 light / 10.38:1 dark. The disabled 보기 추가 button measures 17.22:1 / 15.93:1.
- **Modal focus management is correct on all three counts.** Opening the 취소 dialog moves focus into it and lands on `계속 쓸게요` — the *safe* action, not the destructive one. Six consecutive Tabs cycle `나가기 → ✕ → 계속 쓸게요` and back, every stop reporting `dialog.contains(activeElement) === true`, so focus is genuinely trapped. Escape closes the dialog and returns focus to the 취소 button that opened it.
- **`prefers-reduced-motion` gets an intentional alternative, not a blanket kill.** Under `reducedMotion: 'reduce'` the button transition list drops `transform` while keeping `opacity, background-color, color` at 0.16s, so state changes remain perceptible. The wizard's step-change scroll also branches on `matchMedia('(prefers-reduced-motion: reduce)')` to pick `auto` over `smooth`. No `0.01ms` global override exists.
- **Semantic structure is complete.** Exactly one `<h1>` per page (visible on desktop, visually hidden on mobile where the top bar carries the title), landmarks `header` / `nav[aria-label="주요 메뉴"]` / `main` / `footer` all present, and the step indicator is a real `<ol>` whose three children are `<li>`.
- **Every `aria-describedby` resolves.** DOM probe of all described-by and labelled-by references across step 1 (empty + errors), step 2, and step 3 (empty + errors) returned zero dangling ids in every state.
- **Dropzone accessible names are distinct.** 로고 이미지 / 지도 1 / 지도 2 — the identical-name defect from the previous critique is fixed.
- **Tab order is logical with no traps.** A single continuous pass runs header → 유형 radio → 날짜 → 나들이 이름 → 로고 dropzone → 파일 지우기 → 취소 → 다음, matching visual order. The file-clear button (`44×44`) and the 취소 button (`48×50`) are both keyboard reachable and carry visible rings.

---

## Proposed score

**3 / 4** — WCAG AA is met across contrast, semantics, live regions, focus management, reduced
motion and accessible naming, with axe clean inside the wizard in every state and theme tested.
One real AA failure (2.4.7 on the three dropzones) and one 2.4.11 gap (the radio ring) are the
minor gaps that hold this off 4. This is the "AA mostly met, minor gaps" band; it would be a 4
once the dropzone and radio focus indicators move to their visible controls.
