제품 고유의 디테일이 딱 두 군데 있다. `유형` 라디오가 실제 두 사람의 이름(`AYO`/`RYU` → 아영/일권)이라는 점, 그리고 2단계 힌트 "드라이브 비밀번호는 상세 화면에서 입사일로 안내됩니다" — 둘만 아는 날짜를 비밀번호로 쓰는 규칙. 이 둘은 다른 제품에서 나올 수 없는 문장이다.

문제는 나머지 전부다. 특히 **가장 이 제품다워야 할 3단계 퀴즈 저작이 가장 몰개성하다.** "둘만 아는 놀이"를 만드는 순간인데 화면은 사내 설문 폼처럼 라벨+입력창 12개를 세로로 쌓아둔다.

그리고 결정적으로 — **사진 우선을 표방하는 제품(DESIGN.md §1, §9)의 사진 업로드 화면에 사진이 한 장도 안 보인다.** 로고·지도1·지도2를 올려도 13px 회색 텍스트로 `map.png` 파일명만 뜬다. 방금 고른 지도 캡처가 맞는지 확인할 방법도, 잘못 골랐을 때 지울 방법도 없다.

**놓친 기회들**
- 유형 라디오에 각자의 프로필 사진/색을 얹을 수 있었다. 지금은 이름만 다른 평범한 2지선다다.
- 데스크톱 1440px에 오른쪽 실시간 프리뷰(로고+지도+퀴즈 카드 조립)를 놓을 공간이 있는데, 그냥 넓은 모바일 폼으로 쓰고 있다.
- 저장 직후 `navigate(목록)` 한 줄. 정성껏 만든 퀴즈를 완성한 순간에 아무 보상이 없다.

## Deterministic Scan

`detect.mjs`를 대상 6개 파일과 공용 프리미티브 5개에 각각 실행 → **모두 `[]`, exit 0. 0건.**

**이 0건은 "깨끗하다"는 뜻이 아니다.** Assessment B가 이걸 액면가로 받지 않고 검증했다: `color:'#999999'`·`<div onClick>`·`transition:all` 을 심은 합성 파일을 만들어 같은 디텍터에 돌렸더니 **그것도 `[]`** 를 반환했다. 엔진(`detector/engines/regex/detect-text.mjs`)을 따라가 보니, 비-HTML 소스에 대해서는 Tailwind 유틸리티 클래스·인라인 `style={{}}`·CSS-in-JS 템플릿만 매칭하는 regex 패스만 돌고, `low-contrast`/`tiny-text`/`cramped-padding` 같은 DOM 의존 규칙은 HTML 정적 모드나 URL 모드에서만 동작한다. 이 코드베이스는 외부 스타일시트 + CSS 커스텀 프로퍼티로만 스타일링하므로 정확히 그 사각지대에 들어간다.

따라서 이번 회차의 실질 증거는 CLI 스캔이 아니라 **아래 라이브 DOM 실측**이다.

## Overall Impression

시각 시스템은 잘 서 있다. 라이트·다크 양쪽에서 **측정한 7개 색 쌍이 전부 WCAG AA를 통과**했고(에러 5.47:1, 힌트 5.55:1, 다음 버튼 9.03:1 / 다크에서도 5.74~15.93:1), 관측된 모든 색값이 DESIGN.md 토큰과 정확히 일치했으며, Pretendard는 선언만 된 게 아니라 실제 로드까지 확인됐다(`document.fonts.check` true + `FontFace.status: loaded`). 다크모드에 테마 안 먹은 요소도 없다.

무너진 건 **폼의 행동**이다. 값을 고쳐도 에러가 안 사라지고, 여러 장의 파일과 손으로 쓴 퀴즈 문구를 담은 폼에서 나가는 안전망이 하나도 없다. 사용자가 이 화면을 신뢰할 근거가 없다.

**가장 큰 기회 하나만 고르면:** 3단계를 "퀴즈 폼"이 아니라 "선물 포장"으로 다시 짜는 것. 실시간 미리보기 + 청크 분할 + 저장 후 확인 모먼트. 지금은 이 제품에서 가장 애정이 들어가야 할 작업이 가장 노동집약적이고 보상 없는 구간이다.

## What's Working

1. **`hasSecondMap` 토글의 점진적 공개.** 2번 지도가 필요 없는 다수 케이스에서 폼을 짧게 유지하고, 필요할 때만 지도2·버튼1·버튼2를 노출한다. 초기 인지 부하를 정확히 겨눈 판단이다.
2. **보기 삭제 시 정답 인덱스 재계산.** `useTripRegisterForm.removeQuizOption`(120–149행)이 삭제 인덱스에 따라 `quizAnswer`를 재조정하거나 비운다. 눈에 안 띄는 곳까지 신경 쓴 상태 관리로, "3번 보기를 지웠는데 정답이 엉뚱한 걸 가리키는" 사고를 막는다.
3. **컬러 시스템의 규율.** 실측한 12개 색값이 전부 DESIGN.md 선언 토큰과 일치하고, 라이트→다크 전환에서 회귀가 하나도 없었다. 이 정도로 토큰이 지켜지는 화면은 흔치 않다.

## Priority Issues

### [P0] 값을 고쳐도 에러 문구가 사라지지 않는다 — 데스크톱·모바일 공통

- **What**: 1단계 에러 상태에서 유형·날짜·이름·로고를 전부 올바르게 채워도 "유형을 선택해 주세요" 외 3개가 그대로 남는다(`main-03-step1-filled.png`, `mobile-03`). 3단계도 동일(`main-08`, `mobile-08`).
- **Why it matters**: `useTripRegisterForm.updateField`(72–80행)는 `values`만 갱신하고 `errors`를 건드리지 않는다. `errors`는 `goNext`/`submit`이 재검증할 때만 바뀐다. "고치면 사라진다"는 폼의 가장 기본 계약이 깨져 있다. 사용자는 자기가 뭘 놓쳤다고 오인하거나, 반대로 진짜 에러를 무시하도록 학습한다.
- **Fix**: `updateField`/`updateQuizOption`에서 해당 키의 에러를 즉시 제거하거나, 값 변경 시 해당 필드만 재검증해 `errors`에서 지운다.
- **Suggested command**: `$impeccable harden`

### [P0] 이탈 안전망이 하나도 없다 — 데스크톱 심각, 모바일도 해당

- **What**: `TripRegisterPage.tsx`는 위저드만 렌더링하고, 셸은 전역 헤더/푸터만 준다. 위저드 안에도 페이지에도 "취소"/"목록으로"가 없다. 유일한 탈출구인 헤더 내비 클릭·브라우저 뒤로가기는 확인 없이 즉시 이탈시킨다. 값은 순수 `useState`에만 있어 새로고침 한 번에 전부 사라진다. 모바일 뒤로가기는 있지만 `getDetailMobileBackHref`가 항상 `/mobile`(홈)을 반환해, 정작 저장 성공 시 가는 `/mobile/map`(나들이 목록)과 목적지가 다르다.
- **Why it matters**: 파일 3장 + 손으로 쓴 퀴즈 문구 6줄이 들어간 폼이다. 그리고 **이 문제를 위한 패턴이 이미 코드베이스에 있다** — `DesktopHeader.tsx`의 `isEditDirty` + `ConfirmDialog` 조합이 프로필 편집에 적용돼 있는데, 훨씬 무거운 이 폼에는 재사용되지 않았다.
- **Fix**: 위저드에 명시적 취소 링크 추가, `ConfirmDialog`를 재사용해 dirty 상태 이탈 시 확인, 뒤로가기 목적지를 `/mobile/map`으로 교정. 최소한 `sessionStorage` 임시저장.
- **Suggested command**: `$impeccable harden`

### [P1] 3단계가 청크 없는 12필드 벽이고, 저장 버튼은 두 기기 모두 폴드 아래에 있다

- **What**: `TripRegisterStepQuiz.tsx`는 퀴즈 제목 → 보기 3~6개 → 정답 선택 → 정답 제목/텍스트 → 오답 제목/텍스트를 소제목·카드 구분·여백 단차 없이 한 흐름으로 쌓는다(`slcn-trip-register-step { gap: 1.125rem }` 한 겹뿐). 실측 스크롤: 모바일 390px에서 빈 상태 1359px(1.61 화면), 채운 상태 1743px(2.07 화면). **저장 버튼은 신규 진입 시 모바일 `top:1249.5`(뷰포트 844), 데스크톱 `top:1324.5`(뷰포트 900) — 양쪽 다 폴드 아래.** 게다가 위저드는 단계 전환 시 스크롤을 리셋하지 않는다.
- **Why it matters**: 인지 부하 체크리스트 8개 중 6개를 이 한 단계가 동시에 위반한다(단일 초점/청킹/그루핑/시각 위계/한 번에 하나/선택지 최소화 — 보기를 6개까지 늘리면 정답 선택 라디오가 6지선다가 된다). 그리고 1·2단계에는 첫 에러로 포커스를 옮기는 로직이 없어(3단계에만 `useEffect`가 있다), 에러를 고칠 때마다 긴 스크롤을 위아래로 반복해야 한다.

- **Suggested command**: `$impeccable layout`

### [P1] 접근성 계약이 단계마다 다르다 — 모바일이 더 나쁘다

- **What**: 라이브 DOM 실측 결과 —
  - **모바일 페이지에 헤딩이 0개다.** `h1`~`h6` 쿼리가 빈 배열. 데스크톱만 `<h1>새 나들이 기록하기</h1>`가 있고, 모바일은 `MobileTopBar`가 제목을 `<p>`로 렌더링한다. axe-core가 모바일에서만 `page-has-heading-one`(moderate)을 독립적으로 잡았다.
  - **스텝 인디케이터에 진행 의미가 전혀 없다.** `<span data-active>` 3개뿐 — `aria-current` 없음, `role="list"` 없음, `aria-label` 없음. 스크린리더에는 "3단계 중 1단계"라는 정보가 전달되지 않는다. DESIGN.md §15.4가 명시한 완료/현재/예정 3단계 톤과 커넥터 라인도 구현되지 않고 활성/비활성 2단계뿐이다.
  - **1단계 에러 4개는 `role="alert"`도 `aria-live`도 없다.** 그중 유형·로고 에러는 `id`조차 없어 어떤 `aria-describedby`에도 연결돼 있지 않다. 3단계 퀴즈 에러만 `role="alert" aria-live="assertive"`가 제대로 붙어 있다. 같은 위저드 안에서 품질이 갈린다.
  - **1·2단계 실패 제출 후 `document.activeElement`가 다음/저장 버튼 그대로.** 3단계만 첫 보기 입력으로 이동한다.
  - **드롭존 접근 이름이 프롬프트 텍스트다.** 로고 드롭존의 계산된 접근 이름은 "로고 이미지"가 아니라 `"로고 파일을 끌어다 놓거나 선택하세요PNG · JPG · 최대 10MB"`. 2단계 지도1/지도2는 프롬프트 오버라이드가 없어 **둘의 접근 이름이 완전히 동일**하다 — 스크린리더 사용자는 지금 포커스가 지도1인지 지도2인지 구별할 수 없다.
- **Why it matters**: 전역 `:focus-visible` 링(2px `#A34F6D`)이 잘 깔려 있어 키보드 가시성 자체는 통과하는데, 정작 에러 고지와 위치 파악이 안 된다. 스크린리더 사용자는 "다음을 눌렀는데 아무 일도 안 일어났다"만 경험한다.
- **Fix**: `FileDropzone`의 필드 라벨을 `<label htmlFor>`로 연결하고 `error` prop 지원 추가, 지도2에 고유 프롬프트 부여. 모든 단계 에러에 `role="alert"` + `aria-describedby` 통일. 인디케이터를 `<ol>` + `aria-current="step"`으로. 모바일 톱바 제목을 `<h1>`으로.
- **Suggested command**: `$impeccable audit`

### [P1] 반응형 레이아웃이 양쪽 끝에서 관리되지 않는다

- **What**: 실측 —
  - **1440px**: 카드 폭 **1200px**, 입력창 폭 **1146px**, 좌우 여백 240px. "나들이 이름" 한 줄짜리 텍스트 필드가 1146px로 늘어난다. `.slcn-trip-register-wizard`에 `max-width`가 없어 셸 한계까지 그대로 팽창한다. 1200px는 DESIGN.md가 정의한 세 컨테이너 폭(760 / 1080 / 1440) 중 어느 것도 아니다.
  - **320px**: **세 단계 전부 가로 넘침.** `scrollWidth 338` vs `clientWidth 320`. 원인은 `components-mobile.css`의 `.slcn-shell-detail-mobile .slcn-trip-register-wizard__step-indicator { flex-wrap: nowrap }` + `> span { flex:1 1 0; white-space:nowrap }` — "3개 필을 한 줄에 유지"하려는 의도적 규칙이 320px에서 min-content를 초과해 카드(322px)와 문서 전체를 뷰포트 밖으로 밀어낸다.
- **Why it matters**: 데스크톱은 1440px 공간을 "넓은 모바일 폼"으로 낭비하고, 작은 폰에서는 가로 스크롤이 생긴다. 둘 다 폼 컬럼 폭이 통제되지 않아서 생긴 같은 문제의 양극단이다.
- **Fix**: 폼 컬럼을 640~760px(`layout.content-text`)로 제한하고, 남는 데스크톱 공간은 실시간 프리뷰나 진행 요약에 쓴다. 인디케이터는 좁은 폭에서 `flex-wrap: wrap`을 허용하거나 라벨을 숨기고 번호만 남긴다.
- **Suggested command**: `$impeccable adapt`

## Persona Red Flags

**Jordan (처음 쓰는 사람)** — 유형을 고르고, 날짜를 넣고, 이름을 쓰고, 로고까지 올린 뒤에도 화면에 빨간 글씨 4줄이 그대로다. 로고를 다시 올려보고 라디오를 다시 눌러보다가 "폼이 고장났다"고 결론 낸다. 3단계에서는 `정답1`·`정답2`·`정답3`이라는 라벨을 보고 "정답을 세 개나 쓰라고?"라며 실제 의도(오답 포함 보기 중 하나가 정답)를 오해한다 — 바로 아래 힌트 문구는 같은 것을 "보기"라고 부르는데도.

**Sam (스크린리더 + 키보드 전용)** — 1단계에서 "다음"을 누른다. `role="alert"`가 없어 에러 4개 중 아무것도 읽히지 않고, 포커스는 눌렀던 다음 버튼에 그대로 있다. Sam에게는 버튼이 아무 반응도 하지 않은 것과 구별되지 않는다. 유형 라디오와 로고 드롭존의 에러는 `id`조차 없어 `aria-describedby`로도 도달할 수 없다. 2단계로 넘어가면 지도1과 지도2 드롭존의 접근 이름이 글자 하나까지 같아서 지금 어느 쪽에 파일을 올리는지 알 수 없다. 모바일에서는 페이지에 헤딩이 0개라 헤딩 탐색으로 본문에 진입하는 경로 자체가 없다.

**Casey (한 손, 모바일, 중간에 방해받음)** — 지하철에서 3단계 보기를 입력하다 알림이 온다. 값은 `useState`에만 있어 탭이 회수되면 전부 날아간다. 다시 들어와 저장을 누르려면 1743px 문서에서 아래로 스크롤해야 하고(저장 버튼 `top:1249.5`, 뷰포트 844), 에러가 뜨면 포커스는 안 옮겨져서 위로 올라가 고치고 다시 내려오기를 반복한다. 액션 행은 스티키가 아니다. 뒤로가기(`<`)를 누르면 나들이 목록이 아니라 모바일 홈으로 튕겨나가, 만들던 게 어디 있었는지 다시 찾아야 한다.

## Minor Observations

- **[P2] "끌어다 놓거나 선택하세요"라고 안내하지만 드래그앤드롭은 구현돼 있지 않다.** `FileDropzone.tsx`의 `onDrop={preventDefault}`는 기본 동작만 막고 파일을 받지 않는다. 드롭하면 아무 일도, 아무 메시지도 없이 조용히 무시된다. 있지도 않은 어포던스를 문구로 약속하는 건 오류 예방 위반이다.
- **[P2] 필수 표시 `*`가 퀴즈 보기에만 있다.** `quizTitle`·`quizAnswerTitle`·`quizAnswerText`·`quizErrorTitle`·`quizErrorText`·`date`·`info2`도 전부 `trip-validation.ts`상 필수인데 `required`를 넘기지 않아 표시가 없다.
- **[P2] `정답N` 라벨 ↔ "모든 보기를 입력해 주세요" 힌트가 서로 다른 이름을 쓴다.** 데이터 모델(`OptionCdo { text, isCorrect }`)상 이건 "보기"다. 라벨을 `보기N`으로 바꾸고 라디오 그룹만 "정답 선택"으로 남기면 해소된다.
- **[P3] 위저드 CSS가 디자인 시스템의 입력 규격을 로컬에서 덮어쓴다.** DESIGN.md `text-input`은 `minHeight 48px`, `border 1px hairline`인데 위저드는 `min-height: 2.875rem`(46px), `border-color: border-strong`, 라디오/드롭존은 `1.5px`. 게다가 `1.625rem`·`0.5625rem`·`2.125rem` 같은 일회성 리터럴이 `var(--space-N)`을 대신하고 있다(구현 규칙 #1 위반). CSS 주석이 이유를 밝힌다 — `/* Register: match prototype field/dropzone/radio styling */`. 이 화면은 디자인 시스템이 아니라 프로토타입에 맞춰졌다. 참고로 폰트 **크기**는 전부 램프 위에 있다(13/14/15/28px) — 드리프트는 간격과 테두리 쪽이다.
- **[P3] "지도" / "지도 2" 넘버링이 비일관적**이고, "버튼 1"/"버튼 2"가 실제로 상세 화면 지도 스위처 탭 라벨이 된다는 설명이 어디에도 없다.
- **[P3] 라디오 포커스 링이 필 전체가 아니라 20×20px 네이티브 인풋에만 그려진다.** 클릭 영역은 146×54.5px인데 링은 그 7%에만 붙는다. 터치 타깃 자체는 390px에서 전부 44×44 통과(가장 빠듯한 건 정답 삭제 버튼 46.5×46).
- **[P3] 날짜 입력이 `mm/dd/yyyy`로 표시된다.** Playwright에 `locale: 'ko-KR'`을 명시하고 `navigator.language`가 `"ko-KR"`을 반환하는 컨텍스트에서도 픽셀 단위로 동일하게 재현됐다 — Chromium 네이티브 date 위젯 크롬의 동작이라 페이지 CSS/JS로 제어할 수 없다. 실제 두 사용자의 OS 로케일이 한국어면 다르게 보일 수 있으므로 **실기기 확인 전까지는 단정하지 말 것.** 한국어 표기를 보장하려면 커스텀 데이트 피커가 필요하다.
- **[P3] 데스크톱 라이트 테마에서 등록 라우트 로드 중 401 콘솔 에러 1건** 관측(로그인 이후). 어느 엔드포인트인지는 추적하지 않았다 — 관측만 했고 진단하지 않았다.
- 저장 성공 시 `navigate(목록)` 한 줄뿐. 토스트도 완료 화면도 없다.
